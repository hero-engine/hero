# Hero v0.34.0 candidate notes

Status: **prepared, not published**. These notes describe the candidate diff
from `v0.33.0`. They do not claim that the Apache license, public repository,
tag, release, docs deployment, or launch gates have run.

## Highlights

### Durable project memory is the front door

Hero's public documentation and landing experience now explain the product as
two connected systems: durable project memory carries intent, decisions,
corrections, conventions, evidence, and current state across sessions; the
spec-and-agent delivery loop uses that memory to design, implement, cold-audit,
and verify work.

### Engineering includes lightweight PM and QA help

The default Engineering setup now composes Core, Engineering, and bounded PM
and QA assistance useful during coding work. Focused PM and QA setups remain
optional packs for projects where product management or quality assurance is
the primary workflow. Composition identity, collision detection, deferred
content loading, and domain-aware retrieval keep those modes explicit.

### Focused QA and PM packs

The QA pack adds test strategy, case design, exploratory coverage, regression,
flake, release-readiness, and QA delivery workflows. The PM pack adds product
discovery, prioritization, planning, evidence, release-note, and stakeholder
workflows. Their presence is not a claim that Hero is a broad departmental
platform; public maturity remains bounded by the capability-status page.

### Public trust and onboarding

Root documentation, hosted documentation, and the landing source now use one
executable onboarding path and one product/repository boundary. Contribution,
security, support, conduct, issue, and pull-request surfaces are prepared for
public exposure. A public documentation gate derives mutable inventories,
executes clean-workspace quickstarts, decodes configuration examples with the
production decoder, and verifies deployed revision parity after an approved
deployment.

## Availability boundaries

- Project memory and verified delivery are shipped.
- Attention, Project Mail, Focus, and local project intelligence are shipped
  with the prerequisites documented on the capability-status page.
- Tracker, code-host, cross-repository, and focused domain workflows are
  optional and require explicit setup.
- The headless runtime remains preview.
- Hero Code and Hero Cloud remain separate proprietary products.
- Sprout remains a separate public MIT-licensed project and dependency. It is
  not part of Hero's future Apache-2.0 grant.

## Upgrade notes

There is no known v0.34 workspace-schema migration. After replacing the Hero
binary, run `hero doctor`, then run `hero upgrade` in each existing workspace
to regenerate installed harness content from the new binary. `hero upgrade`
updates Hero's installed project files; it does not replace the binary.

Prebuilt archives require no Go installation. Building from source requires
the Go version declared in `go.mod`.

## Candidate evidence

`scripts/release_candidate.py` builds Darwin, Linux, and Windows archives twice
from one clean revision using deterministic archive metadata. It compares both
builds byte-for-byte, emits SHA-256 checksums, a CycloneDX SBOM, complete
third-party notices, and source provenance, then exercises the native archive
through version, initialization, Codex installation, status, and health checks.

The candidate archives intentionally say that Hero's Apache-2.0 gate is
pending. They are internal verification artifacts and must be rebuilt after an
approved root license is added. Nothing in the candidate builder creates a tag,
uploads to a release repository, or changes source-repository visibility.
