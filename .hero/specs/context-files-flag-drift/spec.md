# `hero context --files` advertised in CLI output and docs but the flag lives on `imports`

## Kickoff

**Status:** completed — string fixes shipped and a self-maintaining `cliHints` registry now guards the binary-emitted invocation surface from this class of drift.

Delivered changes:
- `internal/cli/hints.go` (new) — `cliHints` registry with stable IDs, `Format()` helper, and `cliHintByID(...)` lookup.
- `internal/cli/hints_test.go` (new) — `TestCliHintsResolveAgainstRootCmd` traverses every hint against `rootCmd` and asserts each `--flag` is reachable on the resolved command or its inherited flags; second test guards the lookup helper.
- `internal/cli/relevant.go:232` — printed hint now derived from the registry via `cliHintByID("context-imports-files")`.
- `internal/cli/init.go:288` — generated CLAUDE.md/AGENTS.md template now derived from the same registry entry.
- Seven corpus references in `.hero/specs/` and `.hero/knowledge/` swept from `hero context --files` to `hero context imports --files`.

Validation: drift mutation (changing `--files` → `--filez` in the registry) fails the test with message `hint "..." (id=context-imports-files): flag --filez not found on hero context imports`. Reverted before commit.

Out of scope (filed as follow-up below): the "extract `Examples:` blocks and run them against a fixture workspace" smoke test. The registry catches binary-emitted hint strings; it does not catch advice embedded in cobra `Long`/`Example` blocks.

**Files:** `internal/cli/hints.go`, `internal/cli/hints_test.go`, `internal/cli/relevant.go:232`, `internal/cli/init.go:288`, plus the seven corpus files listed in Change 3.

## Issue

No tracker issue. Surfaced internally as part of a "second instance of command-drift" pattern alongside [`recap-register-missing`](../../specs/recap-register-missing/spec.md). Environment: hero CLI, current main (`95f20d0`).

Symptom for the user: pasting `hero context --files src/foo.go` (as instructed by `hero relevant` output, the generated `CLAUDE.md`, and several internal specs) prints `Error: unknown flag: --files` and exits non-zero. The hint string itself is the bug — the flag exists, but only on a subcommand.

## Investigation

### Evidence — flag lives on the subcommand, not the parent

`internal/cli/context.go` defines two cobra commands:

- `contextCmd` (lines 14–24): the parent `hero context`. Has subcommands `scope` and `imports`. **No flags declared.** Its `Long` description says "Subcommands here emit small, machine-friendly context blocks…" — i.e. it was always intended as a namespace.
- `contextImportsCmd` (lines 51–67): the `imports` subcommand. `RunE: runContextImports`. Its `Long` doc explicitly says "Pass --files to override".

The wiring in `init()` at lines 69–74:

```go
func init() {
    contextCmd.AddCommand(contextScopeCmd)
    contextCmd.AddCommand(contextImportsCmd)
    contextImportsCmd.Flags().StringSliceVar(&contextImportsFiles, "files", nil, "files to scan (defaults to git-status dirty set)")
    rootCmd.AddCommand(contextCmd)
}
```

`--files` is bound to `contextImportsCmd.Flags()`. The parent `contextCmd` has no `.Flags()` call anywhere in the file. Cobra does not inherit subcommand flags upward, so `hero context --files X` rejects `--files`.

### Evidence — CLI output and generated docs advertise the broken form

Two hot, user-facing strings in the binary itself:

1. **`internal/cli/relevant.go:232`** — printed at the end of `hero relevant` output (and by extension, anything that calls into the same passive-nudge surface):

   ```go
   fmt.Println("Run `hero context --files <paths>` for full context, or use `/design` to create a spec for this work.")
   ```

2. **`internal/cli/init.go:288`** — written verbatim into the `CLAUDE.md` (or `AGENTS.md`) generated by `hero init`:

   ```go
   sb.WriteString("and `/deliver` to implement against a spec. Run `hero context --files <paths>` to see\n")
   sb.WriteString("relevant conventions and past work for the files you're touching.\n")
   ```

   That means **every new install regenerates the broken instruction into the agent's project memory** — and the agent reads its own memory file at the start of each session. The miss is self-amplifying.

### Evidence — spec corpus and knowledge notes carry the same stale form

`rg "hero context --files"` across the repo (with hidden) finds seven non-source hits:

- `.hero/specs/conventions-and-decisions/spec.md:28`
- `.hero/specs/prime-command/spec.md:25, 123`
- `.hero/specs/context-injection/spec.md:22`
- `.hero/specs/index-extensions/spec.md:31`
- `.hero/specs/hero-serve-daemon/spec.md:34`
- `.hero/knowledge/notes/buddy-model-architecture/spec.md:36`

These are mostly contextual ("`hero context --files` is the file-based lookup…") rather than runnable commands, but they form a corpus the agent grep's into via `hero relevant` / `hero search`, so they continue to teach the wrong invocation.

### Reproduction

```
$ go run . context --files internal/cli/context.go
Error: unknown flag: --files
... [usage]
exit status 1

$ go run . context imports --files internal/cli/context.go
(prints peer-import signal, or exits 0 quietly)
```

### Root cause

**Code drift after a refactor.** At some point `hero context` was promoted from a single command that took `--files` into a namespace with `scope` and `imports` subcommands (the `imports` subcommand was added in Phase 3 of the cross-repo-peering initiative, per the comment at `internal/cli/context.go:39–46`). When the subcommand was introduced, the `--files` flag moved with it — but the hint strings, the generated CLAUDE.md template, and the existing spec corpus were not updated to reflect the new path.

This is classic command-rename drift: the implementation was refactored correctly; the *documentation and hint surfaces that named the old form* lagged.

`root_cause_class: code` — a logic-adjacent defect where the string literal in the binary no longer matches the CLI surface it's describing. Severity `medium`: user-visible broken instructions, workaround is obvious (`hero context imports --files`), no data loss, but it costs a fresh agent its first turn and erodes trust in the hint surface.

## Code Flow (end-to-end)

How an agent ends up running the broken command:

1. User runs `hero init` in a fresh project.
2. `internal/cli/init.go:288` writes "Run `hero context --files <paths>`…" into the generated `CLAUDE.md`.
3. Agent boots in that project; the harness loads `CLAUDE.md` into session context (per the project-memory feature).
4. Agent edits a file and triggers `hero relevant` (either directly or via a hook).
5. `internal/cli/relevant.go:232` prints "Run `hero context --files <paths>` for full context…" — reinforcing the same broken invocation.
6. Agent shells out: `hero context --files internal/cli/relevant.go`.
7. Cobra dispatches to `contextCmd` (parent). The parent has no `--files` flag.
8. Cobra emits `unknown flag: --files`, prints usage, exits 1.
9. Agent reports failure; user sees the hero-emitted hint contradicting its own CLI surface.

## Goal

When an agent or user follows the on-screen hint or generated CLAUDE.md, the command they run succeeds. The hint is `hero context imports --files <paths>`, and every spec / knowledge note that names the invocation matches.

The `--files` flag stays on `imports`. The `context` parent remains a namespace.

## Suggested Fix Approach

The user lean — **option (b): fix the strings, not the CLI surface** — is the right call. The `context` namespace today has two distinct subcommands (`scope` emits workspace-scope frontmatter cues; `imports` scans changed Go files for peer-owned contract imports). Their inputs and outputs have nothing in common. Lifting `--files` to the parent would either:

- silently apply to both subcommands when invoked at the parent level (confusing — `scope` has no use for `--files`), or
- require duplicating the flag at the parent purely as an alias, with a hidden delegation rule.

Either form muddies the namespace. The cleaner fix is to teach the hint strings and corpus to name the subcommand correctly.

### Change 1 — `internal/cli/relevant.go:232`

**Before:**
```go
fmt.Println("Run `hero context --files <paths>` for full context, or use `/design` to create a spec for this work.")
```

**After:**
```go
fmt.Println("Run `hero context imports --files <paths>` for full context, or use `/design` to create a spec for this work.")
```

**Why:** the printed hint must name a runnable command. The flag is on the `imports` subcommand.

### Change 2 — `internal/cli/init.go:288`

**Before:**
```go
sb.WriteString("and `/deliver` to implement against a spec. Run `hero context --files <paths>` to see\n")
sb.WriteString("relevant conventions and past work for the files you're touching.\n")
```

**After:**
```go
sb.WriteString("and `/deliver` to implement against a spec. Run `hero context imports --files <paths>` to see\n")
sb.WriteString("relevant conventions and past work for the files you're touching.\n")
```

**Why:** the generated `CLAUDE.md` (or `AGENTS.md`) is the agent's first context surface in a new install. Same correction so the wrong form stops propagating into every new project.

### Change 3 — spec corpus sweep

- `.hero/specs/conventions-and-decisions/spec.md:28`
- `.hero/specs/prime-command/spec.md:25` and `:123`
- `.hero/specs/context-injection/spec.md:22`

- `.hero/specs/hero-serve-daemon/spec.md:34`
- `.hero/knowledge/notes/buddy-model-architecture/spec.md:36`

These are descriptive prose, not runnable scripts, but they form the corpus that `hero relevant` and `hero search` surface back to agents — keep them honest. A blanket `rg`/`sed` is appropriate here; no semantic edits, just string substitution.

## Follow-ups

- **Examples-block smoke test.** The registry covers binary-printed hints. It does not cover invocation strings embedded in cobra `Long` / `Example` blocks. A separate spec should extract every `Examples:` block and execute it against a fixture workspace to catch drift in command help text.
- **Corpus drift.** This delivery hand-edited seven `.hero/specs/...md` and one `.hero/knowledge/...md` file. Those references aren't validated by any test — `hero check` could grow a rule that scans the spec corpus for known-stale invocations, but that needs curation. The companion to `recap-register-missing` is the natural place to track that.

## Boundaries

- **No CLI surface change.** Do not lift `--files` to the parent `contextCmd`. Do not rename `imports` to something more generic. The namespace design (scope + imports as two distinct emitters) is correct.
- **No new flag, no alias.** Do not add a deprecated-alias shim — the bad form has never worked, so there's no installed-base to maintain compatibility with.
- **Don't touch `hero context scope`.** It's a separate subcommand with its own purpose, unrelated to this hint.
- **Don't rewrite the prose around the references in `.hero/specs/...`** beyond the literal command substitution. Those specs describe their own work, not this fix.

## Test Plan

### Existing test review

- `internal/cli/context_test.go` — does not exist. There is no test covering the parent vs. subcommand flag wiring.
- `internal/cli/init_test.go` — exists; covers `hero init` output but does not assert on the CLAUDE.md template text containing a *runnable* hint.
- `internal/cli/relevant_test.go` — exists; covers the relevant-nudge rendering but likely does not assert that the printed hint is a valid CLI invocation.

Confirm those files' coverage before adding new tests.

### New tests / changes needed

1. **Round-trip test on hint strings (recommended — see Related Concerns).** Extract the printed hints into testable constants or use a small "executable hint" registry. In a test, parse each hint as a cobra command line and assert `rootCmd.Find(args)` returns a non-error match. This catches the exact class of drift this bug represents.

2. **String-presence regression test** for the two changed surfaces:
   - `internal/cli/relevant_test.go` — assert the output of the `hero relevant` rendering for a sample input contains the substring `hero context imports --files` and does **not** contain `hero context --files <paths>` (the broken form).
   - `internal/cli/init_test.go` — assert the generated CLAUDE.md contains `hero context imports --files` and not the bare `hero context --files`.

3. **Manual reproduction check** — `go run . context imports --files internal/cli/context.go` succeeds; `go run . context --files internal/cli/context.go` still fails (as designed — we're not adding the flag).

### Regression scope

- Anyone scripting against the literal output of `hero relevant` (very unlikely — it's a narrative hint, not a contract) could break. Acceptable.
- `hero init` regenerating CLAUDE.md in existing projects could create a churn diff line on next install. Acceptable, and arguably the point.

## Related Concerns

This is the **second** bug in this batch where a CLI command name lingered in user-facing surfaces after a refactor — the first is [`.hero/specs/recap-register-missing/spec.md`](../../specs/recap-register-missing/spec.md), where `/deliver` and `/diagnose` tell the agent to run `hero recap register/unregister` against a command that has no such subcommands.

Two instances mean it's worth treating as a class. Two complementary options, listed in increasing strength:

### Option A — `hero check` rule that greps for stale invocations

Add a rule to `hero check` that scans `.hero/specs/`, `.hero/knowledge/`, `commands/`, and generated docs for known-stale command forms. The check loads a small allowlist file (e.g. `internal/check/stale_commands.go`) and reports any hit. Initial entries:

- `hero context --files` (not followed by a subcommand)
- `hero recap register`
- `hero recap unregister`

Pros: catches the existing corpus, easy to extend, runs as part of standard health check.
Cons: requires curation — someone has to add an entry per known-stale form. Misses brand-new drift until reported.

### Option B — assert hints are executable as CLI args

Strongly preferred long-term. Extract every printed-to-user "Run `hero …`" hint into a constant or a tiny registry of `Hint{Text string, Args []string}`. In a unit test, for each hint, build the cobra command tree (the existing `rootCmd`), call `rootCmd.Find(args)`, and assert no `unknown command` / `unknown flag` error.

Concrete shape:

```go
// internal/cli/hint_test.go
func TestHintsAreExecutable(t *testing.T) {
    for _, h := range cli.AllHints() {
        cmd, _, err := rootCmd.Traverse(h.Args)
        require.NoError(t, err, "hint %q: %v", h.Text, err)
        require.NoError(t, cmd.ParseFlags(h.Flags), "hint %q: bad flags", h.Text)
    }
}
```

Pros: catches drift the day someone renames a flag or moves a command, with **zero curation**. Self-maintaining.
Cons: requires the small refactor to lift hint strings into a registry. Doesn't cover descriptive prose in `.hero/specs/...` — only the strings the binary itself emits.

**Recommendation:** ship Option B alongside this fix. It's the lighter-touch and self-maintaining of the two. Option A is worth following up as a separate spec if the spec corpus turns out to be a frequent drift source — but the binary-emitted hint surface is where the highest-leverage stale strings live (because they reach every user), and Option B closes that loop completely.

If Option B is out of scope for the same delivery as the string fix, file it as a child of `spec-status-integrity` or its own slug.

## Recap

`hero context --files` was promoted into a `context` namespace with `scope` and `imports` subcommands; the `--files` flag moved to `imports`, but two binary-emitted hint strings (`internal/cli/relevant.go:232` and `internal/cli/init.go:288`) and seven spec / knowledge references still name the old form. Fix the two binary strings and sweep the corpus — don't lift the flag back up, because `context` is a coherent namespace and the two subcommands have nothing in common. Companion concern: this is the second command-drift bug this batch (alongside `recap-register-missing`); add a self-maintaining test that asserts every printed `hero …` hint parses against the cobra tree.
