## Captured

User report (2026-05-08):

> "when resuming a session, if the current binary is older than the
> last session, the agent will try to 'upgrade' the workspace to an
> older version and cause a lot of churn on knowledge files. Upgrade
> should not be allowed to downgrade a workspace."

## Investigation

### Summary

| Attribute | Assessment |
|-----------|------------|
| **Criticality** | **high** — causes unnecessary file churn, git noise, and potential loss of workspace state when agents auto-respond to mismatch warnings |
| **Ease of Fix** | **easy** — add a version direction check in two places; no architectural changes needed |
| **Caused by our codebase?** | **Yes** — `Mismatch()` and `runUpgrade()` both lack direction-aware version comparison |
| **Needs more research?** | **No** — root cause is confirmed through code tracing |

### Background

When a user resumes a session with a hero binary that is **older** than the binary that last touched the workspace (e.g., user has two machines with different hero versions, or rolled back to an older binary), the system treats the version mismatch identically to the "binary is newer" case. The `Mismatch()` function returns a generic warning suggesting `hero upgrade`, and `runUpgrade()` proceeds to overwrite workspace files with the older binary's embedded content — effectively **downgrading** the workspace.

The original design spec (`version-tracking-upgrade`) explicitly stated: "If the binary is **newer**, print a one-line warning." The implementation never enforced this direction check.

### Analysis

The bug has two independent failure points:

1. **`Mismatch()` (version.go:150-170)** — Only checks string equality (`info.HeroVersion == binaryVersion`). Returns the same warning message regardless of whether the binary is newer or older. The message always says "run 'hero upgrade' to update" which is misleading when the binary is older.

2. **`runUpgrade()` (upgrade.go:53-183)** — Never checks version direction. If versions differ (line 77: `fromVersion == binaryVersion`), it proceeds to copy embedded files and stamp the workspace with the binary's version — even if that version is older.

### Root Cause

**No semantic version comparison exists anywhere in the codebase.** The version system uses string equality only. There is no concept of "newer" vs "older" — only "same" vs "different."

### Source

| File | Lines | Role |
|------|-------|------|
| `internal/version/version.go` | 150-170 | `Mismatch()` — string equality only, no direction check |
| `internal/cli/upgrade.go` | 53-183 | `runUpgrade()` — proceeds with file overwrite regardless of version direction |
| `internal/cli/root.go` | 34-51 | `PersistentPreRun` — calls `Mismatch()` on every command, prints warning |
| `internal/cli/status.go` | 191-196 | Shows "upgrade available" regardless of direction |

### Fix Direction

1. Add a `CompareVersions(a, b string) int` function that returns -1 (a < b), 0 (equal), or 1 (a > b) using semantic version comparison.
2. Update `Mismatch()` to return distinct results for "binary newer" (upgrade available) vs "binary older" (downgrade detected, no action needed).
3. Update `runUpgrade()` to reject the operation with a clear error when binary version < workspace version.
4. Update `status.go` to not show "upgrade available" when binary is older.

## Problem Statement

**Reproduction scenario:**
1. User runs `hero init` on Machine A with hero v0.3.0 → workspace stamped at v0.3.0
2. User switches to Machine B with hero v0.2.5 (older binary)
3. User runs `hero resume` (or any command) → `PersistentPreRun` calls `Mismatch()`
4. `Mismatch()` returns: "workspace was created with v0.3.0, binary is v0.2.5 — run 'hero upgrade' to update"
5. Agent sees this warning and runs `hero upgrade`
6. `runUpgrade()` copies v0.2.5's embedded agents/commands/skills files over the v0.3.0 versions
7. `StampUpgrade()` writes v0.2.5 to `version.json`
8. Result: workspace files are downgraded, knowledge files may be regenerated by subsequent scans, causing git churn

**The mismatch warning is also misleading.** It says "run 'hero upgrade' to update" when in fact upgrading would make things worse (downgrade the workspace).

## Root Cause Analysis

**Confirmed root cause: Missing version direction check in two locations.**

### Evidence 1: `Mismatch()` uses string equality only

From `internal/version/version.go:150-170`:

```go
func Mismatch(heroDir, binaryVersion string) string {
    if binaryVersion == "" || binaryVersion == "dev" {
        return "" // dev builds don't warn
    }
    info, err := Read(heroDir)
    if err != nil || info == nil {
        return "" // no version file = pre-version workspace, don't warn
    }
    if info.HeroVersion == "" || info.HeroVersion == "dev" {
        return "" // workspace was created with dev build
    }
    if info.HeroVersion == binaryVersion {
        return "" // versions match
    }
    return fmt.Sprintf("workspace was created with v%s, binary is v%s — run 'hero upgrade' to update",
        cleanVersion(info.HeroVersion), cleanVersion(binaryVersion))
}
```

The only comparison is `info.HeroVersion == binaryVersion` (line 164). If they differ, the same warning is returned regardless of direction. There is no `>` or `<` comparison.

### Evidence 2: `runUpgrade()` has no direction guard

From `internal/cli/upgrade.go:77-82`:

```go
if fromVersion == binaryVersion && fromVersion != "dev" {
    fmt.Printf("Workspace is already at v%s — nothing to upgrade.\n", binaryVersion)
    return nil
}
fmt.Printf("Upgrading workspace from v%s to v%s\n\n", fromVersion, binaryVersion)
```

The only early exit is when versions are equal. If `fromVersion` is "0.3.0" and `binaryVersion` is "0.2.5", the function proceeds to "upgrade" from 0.3.0 to 0.2.5 — a downgrade.

### Evidence 3: No semver comparison exists in the codebase

A search for `semver`, `CompareVersion`, `version.*compare`, `less.*than`, `older.*than`, `newer.*than` across the entire codebase found **zero** semantic version comparison implementations. The only version comparison is string equality.

### Evidence 4: Original spec intended direction-aware behavior

The completed spec `version-tracking-upgrade` states:

> "If the binary is **newer**, print a one-line warning to stderr"

The implementation never enforced this constraint.

## Notes

- The fix should use a simple semver comparison. Hero versions appear to follow `MAJOR.MINOR.PATCH` format (e.g., "0.2.3", "0.3.0"). A lightweight comparison function that splits on `.` and compares integer components is sufficient — no need for a full semver library.
- The `Mismatch()` function currently returns a `string` (warning message or empty). To support direction-aware behavior, it could either: (a) return a struct with direction + message, or (b) return different messages for upgrade vs downgrade, or (c) return a typed result. Option (b) is the simplest change with minimal API impact.
- The `runUpgrade()` guard should be an early return with a clear error message, not a silent no-op. The user should understand why the operation was rejected.

## Recap

The bug is caused by missing version direction checks in two places: `Mismatch()` treats all version differences identically, and `runUpgrade()` proceeds with file overwrites regardless of whether the binary is newer or older than the workspace. This causes workspace downgrades when users switch to older binaries, resulting in knowledge file churn. The fix requires adding semantic version comparison and direction-aware guards in both functions. Severity is high because it causes unnecessary file modifications and misleading user messages.

## Root cause

**Missing version direction comparison.** The `Mismatch()` function in `internal/version/version.go` uses only string equality (`==`) to compare versions, returning the same warning for both "binary newer" and "binary older" scenarios. The `runUpgrade()` function in `internal/cli/upgrade.go` has no guard against downgrading — it proceeds with file overwrites whenever versions differ, regardless of direction. The original design spec explicitly stated the warning should fire "if the binary is newer," but this constraint was never implemented.

## Fix design

### Change 1: Add version comparison function

**File:** `internal/version/version.go`

Add a `CompareVersions(a, b string) int` function that performs semantic version comparison:
- Returns `-1` if `a < b` (a is older)
- Returns `0` if `a == b`
- Returns `1` if `a > b` (a is newer)

Implementation: split on `.`, parse each component as int, compare left-to-right.

### Change 2: Update `Mismatch()` to be direction-aware

**File:** `internal/version/version.go`, lines 150-170

Replace the single warning message with direction-specific messages:
- If `binaryVersion > workspaceVersion`: "workspace was created with v{ws}, binary is v{bin} — run 'hero upgrade' to update"
- If `binaryVersion < workspaceVersion`: "workspace was last used with v{ws}, binary is v{bin} — downgrade detected, no action needed"
- If equal: return "" (unchanged)

### Change 3: Add downgrade guard to `runUpgrade()`

**File:** `internal/cli/upgrade.go`, after line 76 (before the "already at version" check)

Add an early return when `binaryVersion < workspaceVersion`:
```
if binaryVersion != "dev" && fromVersion != "unknown" && fromVersion != "dev" {
    cmp := version.CompareVersions(binaryVersion, fromVersion)
    if cmp < 0 {
        return fmt.Errorf("cannot downgrade workspace from v%s to v%s — use a newer hero binary or run 'hero init' to create a fresh workspace", fromVersion, binaryVersion)
    }
}
```

### Change 4: Update `status.go` version display

**File:** `internal/cli/status.go`, lines 194-195

Only show "upgrade available" when binary is newer than workspace:
```
if wsVersion != "unknown" && wsVersion != binaryVersion {
    cmp := version.CompareVersions(binaryVersion, wsVersion)
    if cmp > 0 {
        versionStr += fmt.Sprintf(" (workspace %s — upgrade available)", wsVersion)
    }
}
```

### Change 5: Add tests

**File:** `internal/version/version_test.go`

Add tests for:
- `TestCompareVersions` — various version pairs (equal, newer, older, different component lengths)
- `TestMismatch_BinaryNewer` — confirms upgrade warning
- `TestMismatch_BinaryOlder` — confirms downgrade message (or no warning, depending on design choice)
- `TestMismatch_SameVersion` — confirms no warning (already exists)

**File:** `internal/cli/upgrade_test.go`

Add test for:
- `TestUpgrade_DowngradeRejected` — confirms error when binary is older than workspace

## Acceptance criteria

**AC-1:** `hero upgrade` rejects the operation when the binary
version is older than the workspace version recorded in
`version.json`. Returns a clear error message explaining the
mismatch.

**AC-2:** `hero resume` (and any other path that calls into
version mismatch detection) does not trigger workspace file
rewrites when the binary is older than the workspace version.

**AC-3:** Knowledge files (`.hero/knowledge/`) are not modified
during a resume when the binary version is older than the workspace
version.

**AC-4:** The version mismatch warning message distinguishes between
"binary newer than workspace" (upgrade available) and "binary older
than workspace" (downgrade detected, no action).

## Out of scope

- Changing how `hero upgrade` works when binary IS newer (that path
  is fine).
- Auto-upgrade behavior (if it exists) — this bug is specifically
  about preventing downgrade.

## Open questions

- Is the downgrade triggered by `hero resume`, `hero scan`, or the
  agent's own logic reading the mismatch warning?
  **Answer:** The agent reads the mismatch warning from `PersistentPreRun`
  (fires on every command including `resume`) and runs `hero upgrade`.
  The warning previously said "run 'hero upgrade' to update" regardless
  of direction, so the agent would dutifully downgrade.
- What exactly causes the "churn on knowledge files" — is it
  `hero upgrade` rewriting knowledge files, or something else?
  **Answer:** `hero upgrade` rewrites all embedded files (agents/,
  commands/, skills/) from the older binary's embedded filesystem.
  Subsequent `hero scan` then regenerates knowledge files based on
  the downgraded agents/commands, causing additional git churn.
