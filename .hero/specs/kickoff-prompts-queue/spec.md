## Kickoff

Adds a `## Kickoff` section to every spec and ships `hero queue` / `hero list` so paste-ready cold-start prompts surface for every parallel work path — not just the one NEXT.md captures.

**Status:** completed — six phases shipped across commits `0052c84..5bcaf02`. The spec itself is the integration test: it carries its own kickoff, surfaces in `hero queue`, and routes through the new MCP tools.

**Pick up at:** the lived-experience pass — start a fresh session, paste a kickoff from `.hero/QUEUE.md`, see if the floor actually rises. Re-run `hero next install-hooks` first so the pre-commit hook picks up `hero queue write`.

→ `hero queue --format kickoff`

**Files:** [skills/kickoff-prompt.md](skills/kickoff-prompt.md), [internal/spec/select.go](internal/spec/select.go), [internal/cli/list.go](internal/cli/list.go), [internal/cli/queue.go](internal/cli/queue.go), [internal/serve/mcp.go:1065](internal/serve/mcp.go:1065)

## Goal

Make a fresh agent session productive from prompt 1 — not by injecting more context per session, but by giving every spec its own paste-ready kickoff and surfacing all ready specs as a ranked queue. The user pastes one short block and the model is in the work; or runs `hero queue` to pick from a list of ready paths instead of asking *"what should I work on next?"*

Three artifacts shipped together because they share infrastructure and the queue is meaningless without per-spec kickoffs:

1. **`## Kickoff` section on every spec** — terse, model-optimized, authored inline by spec-writing skills (`/design`, `/deliver`) and refined by the user. No projection magic, no hook regen — it's just part of the spec.
2. **`hero queue` — root command** — graph-projected ranked list of ready-to-work specs with their kickoffs, on demand. No persistence; queries the DB every call.
3. **`hero list` — root command** — full filterable listing of *any* spec type with flag-driven querying. The power-user counterpart to `hero queue`'s curated front door.

## Problem

Today's cold-start workflow:

1. User hits a context limit or finishes a chunk and decides to switch tracks.
2. User asks the assistant: *"give me a prompt to paste into a new session for X"* (or *"give me prompts for the next two paths I could work on"*).
3. Assistant generates a verbose, free-form briefing — usually 80% duplicated from the spec, 20% session-specific glue.
4. User pastes it. Productive again.

Pain:

- **Verbose duplication.** Every session-handoff prompt re-derives content already in the spec — Goal, Problem, current Status, recent commits. Wasted tokens, wasted user time.
- **No persistence.** Nothing saves these. The user has asked *"should we save these somewhere?"* multiple times. NEXT.md only holds *one* path forward (the current session); parallel tracks aren't surfaced.
- **No queue visibility.** "What could I be working on?" has no canonical answer surface. `hero list` returns specs but not "ready to dig in" with a paste-ready opener. `hero blocked` is the inverse and the user doesn't know what *isn't* blocked at a glance.
- **Mission leak.** Hero's promise — *every session starts as smart as the last one ended* — partially fails when the user has to hand-craft session openers each time. Floor-raising means a brand-new clone with no muscle memory should also pick a track and go.

`agent-cold-start` already solved the single-session-handoff case (NEXT.md). This spec generalizes the same idea to the *backlog* — every spec is a potential next session, so every spec needs a session-opener.

## Design

### Kickoff is part of the spec, authored by skills

A new `## Kickoff` section lives in `spec.md`, between `## Goal` and `## Problem`. **It's not projected. It's not auto-generated by a hook. It's part of the spec format, same as `## Acceptance Criteria` or `## Changes`.**

Who writes it:

- **`/design`** writes the initial kickoff when scaffolding a new spec. The skill — `kickoff-prompt` — defines the format and quality bar.
- **`/deliver`** rewrites the kickoff at status flips (planning→delivering, after a meaningful chunk lands) so it always reflects "where to pick up *now*."
- **The user** can hand-edit at any time, same as any other section. No lock flag needed — the spec is the source of truth, every edit is intentional.

Why this is better than a hook:

- A heuristic hook is a *lossy approximation* of what `/design` already does well. The skill has the model in the loop with full spec context — it produces a real kickoff, not a stitched template.
- No `kickoff_tuned` flag. No `kickoff_updated` frontmatter. No `--force` override semantics. The simpler model means fewer bugs, fewer edge cases.
- Hooks should not depend on model calls (latency, reliability, predictability). And a heuristic-only hook is the lossy version. So: no hook.
- Stale kickoffs are *visible*: the user reads them when they paste them. If a kickoff says "pick up at X" and X already shipped, the user runs `/deliver` (or just edits inline) and moves on. The fix is the same fix that's already in the workflow.

A single optional frontmatter field for sort stability:

```yaml
pinned: true   # floats this spec to the top of `hero queue`
```

That's the only manual override. Everything else lives in the section body or the graph.

### Kickoff section format (defined by `skills/kickoff-prompt.md`)

Target 60–120 tokens. Hard cap 200. Aggressive — it's a prompt, not documentation.

The full format definition with worked examples lives in [skills/kickoff-prompt.md](skills/kickoff-prompt.md). The shape:

- **First line** — what this spec is, in the user's vocabulary.
- **Status** — one of planning / delivering / blocked / in-review, plus a half-sentence on the last meaningful turn.
- **Pick up at** — the concrete next step, 1–2 lines.
- **→ pointer** — a runnable spec path, slash command, or shell command.
- **Files** — 2–5 path:line refs the model will need to open first.
- **Skip** (optional) — one line per approach already rejected.

Sections after Files are omitted when empty. The skill defines the quality bar — `hero check` enforces presence (every non-completed spec has the H2), not internal structure. See [skills/kickoff-prompt.md](skills/kickoff-prompt.md) for the literal markdown template and worked examples.

### `hero queue` — root command, DB-projected

The queue is computed on demand from the graph DB every call. No file persistence, no merge surface, no staleness window — query the DB, render the answer, done.

```
hero queue [--limit N] [--horizon now|next|later] [--mine] [--format text|json|kickoff]
```

Default behavior: prints ready specs in ranked order, each as `<slug> — <title>` header + the `## Kickoff` body, separated by `---`. Default format is `kickoff` (paste-ready blocks). `--format text` strips kickoff bodies down to one-liners.

**Ranking signals**, applied in order:

1. **Pinned** — `pinned: true` floats to the top regardless of other signals.
2. **Status:** `delivering` > `planning` > everything else open.
3. **Horizon:** `now` > `next` > `later`.
4. **Dependency readiness:** any hard `relations.depends_on` target not in `completed` excludes the spec entirely (it belongs in `hero blocked`, not `hero queue`).
5. **Recency:** more recently touched (commit, status flip, kickoff edit) ranks higher. Stale > 30 days drops one rank tier.

Excluded: status in `{completed, archived, abandoned}`; specs missing a `## Kickoff` section (warned in `hero check`).

### `hero list` — root command, full filtered listing

`hero queue` is curated and ranked; `hero list` is the power-user query tool. Returns any spec type with flag-driven filters and free choice of sort/format.

```
hero list
  [--type feature|bug|convention|decision|initiative|rule|context]
  [--status planning|in-review|delivering|completed|archived|abandoned]
  [--horizon now|next|later]
  [--tag <tag>]                  (repeatable)
  [--ready]                      (only specs eligible for `hero queue`)
  [--blocked]                    (only specs with unmet deps; complements --ready)
  [--pinned]
  [--mine]                       (touched by current git user in last 30 days)
  [--stale [days]]               (no activity for N days, default 30)
  [--sort recency|status|alpha|priority]   (default: recency)
  [--limit N]
  [--format text|json|table|kickoff]
```

Defaults: no filters → all open (non-completed) specs, sorted by recency, table format.

`hero queue` is *roughly* equivalent to `hero list --ready --sort priority --format kickoff`, with curated defaults. Both exist because `queue` is the daily front door (low-friction, opinionated) and `list` is the query surface (composable, neutral).

Implementation note: `hero list` is the workhorse query under both. `hero queue` calls into the same selector with the curated flag set so we don't have two ranking implementations.

### MCP tool surface

Three new tools, mirroring the CLI:

- `hero_kickoff(slug)` — return the `## Kickoff` body for a spec. Lets the model self-serve when the user says *"give me a session-opener for spec X."*
- `hero_queue(limit?, horizon?)` — ranked ready queue with kickoff bodies. Lets the model answer *"what should I work on?"* by reading directly, summarizing options, and presenting choices.
- `hero_list(type?, status?, horizon?, tag?, ready?, blocked?, pinned?, mine?, stale?, sort?, limit?)` — full filtered listing. The query primitive that other agent flows can call when they need a slice of the spec corpus.

All three are read-only and additive. They route through the same selector code as the CLI; no parallel logic.

### `.hero/QUEUE.md` — pre-rendered snapshot for harnesses without terminal access

Some harnesses (Claude Code, notably) can't open a terminal mid-session-start — the user can't run `hero queue` to see what's up before pasting their first prompt; they'd have to burn a turn asking the agent, or alt-tab to a separate terminal app. Opencode handles this better; we shouldn't *require* it.

Fix: `hero queue` also writes its rendered output to `.hero/QUEUE.md` — a pre-projected snapshot. The DB stays the source of truth; the file is a convenience surface the user can open in any editor without leaving the session.

- Regenerated by the same pre-commit hook that already manages NEXT.md (extend the managed block from `pre-commit-auto-stage-next` to also call `hero queue write` and stage `.hero/QUEUE.md`).
- Also regenerated on `/handoff`, `/deliver`, and end-of-`/design` (any moment a spec's status or kickoff changes).
- Fully overwritten every refresh — never hand-edited, no agent half, no merge complexity. Same `merge=hero-next` driver pattern works on it.
- Format: identical to `hero queue --format kickoff` output. What you'd see in the terminal is what you read in the file.

This is *not* a replacement for the DB query — it's a staleness-tolerant cache. If the user has just made changes and wants a fresh view, they run `hero queue` (or the agent calls `hero_queue` via MCP). If they're starting cold and just want to see what's up, they open the file.

### Two spin-off targets — interactive vs. autonomous

The kickoff prompt is the artifact for one specific case: **the user wants to pick the work back up themselves in a new interactive session**. Different from autonomous handoff. Hero already has both:

| Spin-off shape | Mechanism | Why |
|---|---|---|
| Interactive — user pastes into a fresh chat | `hero_kickoff <slug>` (this spec) | User stays in the loop; needs a paste-ready opener that primes the model fast. |
| Autonomous — agent runs headless, opens a PR | `hero agent run deliver <slug>` (from `async-delivery`) | Spec is complete enough that no live oversight is needed; the agent loads the spec corpus directly — no kickoff prompt required. |

These compose. The recap rule (`agent-end-of-turn-recap`) picks the right offer based on the chunk's shape: well-specced + AC-clear → `hero agent run`; needs human judgment / exploratory → `hero_kickoff`. The kickoff prompt is *only* for the interactive case; making it carry autonomous-handoff weight too would bloat both surfaces.

### How this composes with existing workflows

- **`/design`** — at end-of-skill, write the `## Kickoff` section. (Skill update; no infra change.)
- **`/deliver`** — at status flip and at end-of-meaningful-turn, rewrite `## Kickoff`. (Skill update.)
- **`/diagnose`** — same pattern when bug specs flip from `triaging` → `delivering`.
- **`/resume`, `/prime`** — surface `hero queue` output as part of priming so the user sees the ranked list at session start. The kickoff is what you paste *to get in*; `/resume` runs from a warm slate once you're in.
- **`hero check`** — flags any non-completed spec missing `## Kickoff` and recommends running `/design` or hand-editing. Also flags kickoffs whose `Pick up at:` line references already-completed AC (heuristic drift detector — non-blocking, advisory).
- **`pre-commit-auto-stage-next`** — unchanged. NEXT.md still travels with commits. Queue is not in NEXT.md, so no merge surface added.

### What's explicitly NOT shipping

- **No projection of the queue into NEXT.md.** NEXT.md stays the single-session handoff it already is. The queue gets its own file (`.hero/QUEUE.md`) so cold-start doesn't crowd the active-session artifact.
- **No `kickoff_tuned` lock flag, no `kickoff_updated` frontmatter, no auto-refresh hook.** The kickoff is written by skills and humans. If it's stale, the fix is the existing workflow.
- **No federation across repos.** `cloud-mcp` owns cross-repo surfacing.
- **No AI-driven priority scoring.** Ranking is heuristic + `pinned: true`.
- **No queue history / archive.** `git log` of `spec.md` files captures kickoff evolution per spec; the queue is always "now."
- **No `hero kickoff` parent command.** The kickoff is part of the spec — there's no command surface for it beyond `hero spec show <slug>` (which already exists or is trivial). MCP gets `hero_kickoff` because models need direct access; CLI users `cat` the spec or use `hero list --format kickoff`.
- **No replacement for `/resume` or `/prime`.** Composes with them.

## Acceptance Criteria

### `## Kickoff` section

- THE SYSTEM SHALL ship a `kickoff-prompt` skill in `skills/` defining the section format, content guidance, and quality bar.
- WHEN `/design` scaffolds a new spec THE SYSTEM SHALL include a populated `## Kickoff` section between `## Goal` and `## Problem`.
- WHEN `/deliver` flips a spec's status THE SYSTEM SHALL rewrite the `## Kickoff` section to reflect the new pick-up point.
- THE SYSTEM SHALL preserve the `## Kickoff` body verbatim when round-tripping a spec through the parser (no whitespace or formatting drift).
- THE SYSTEM SHALL target kickoff bodies of 60–120 tokens with a hard cap of 200 (skill enforces; not parser-validated).
- THE SYSTEM SHALL not introduce `kickoff_tuned`, `kickoff_updated`, or any other tuning frontmatter — the kickoff is the spec's content, not a projection.

### `hero queue` and `hero list`

- WHEN `hero queue` runs THE SYSTEM SHALL return ready specs ranked by pinned / status / horizon / dependency-readiness / recency, each rendered with its `## Kickoff` body, separated by `---`.
- WHEN `hero list` runs with the full flag set THE SYSTEM SHALL filter and sort across all spec types per the flags and emit the requested format (`text|json|table|kickoff`).
- WHEN `hero list --ready` runs THE SYSTEM SHALL apply the same readiness filter as `hero queue` (without the curated default sort/format).
- WHEN `hero list --blocked` runs THE SYSTEM SHALL return specs with at least one unmet hard dependency (complement of `--ready`).
- IF a spec has any `relations.depends_on` target not in `completed` status THEN THE SYSTEM SHALL exclude it from the ready set.
- WHERE a spec's status is in `{completed, archived, abandoned}` THE SYSTEM SHALL exclude it from the ready set by default.
- WHERE `pinned: true` is set on a spec THE SYSTEM SHALL float it to the top of the ready set regardless of other ranking signals.
- THE SYSTEM SHALL share a single ranking-selector implementation across `hero list`, `hero queue`, the MCP tools, and the QUEUE.md projection.

### `.hero/QUEUE.md` snapshot

- WHEN `hero queue write` runs THE SYSTEM SHALL render the current ranked queue to `.hero/QUEUE.md`, fully overwriting prior content.
- WHEN the pre-commit hook runs THE SYSTEM SHALL invoke `hero queue write` and stage `.hero/QUEUE.md` alongside the existing `.hero/NEXT.md` and `.hero/next/*.md` paths.
- WHEN `/handoff` runs THE SYSTEM SHALL refresh `.hero/QUEUE.md`.
- WHEN `/design`, `/deliver`, or `/diagnose` complete a spec mutation THE SYSTEM SHALL refresh `.hero/QUEUE.md`.
- THE SYSTEM SHALL register a merge driver (or extend `merge=hero-next`) so `.hero/QUEUE.md` is regenerated rather than text-merged on conflicts.
- THE SYSTEM SHALL commit `.hero/QUEUE.md` (not gitignored) so the file travels across machines.

### MCP tools

- WHEN the model invokes `hero_kickoff(slug)` via MCP THE SYSTEM SHALL return the spec's `## Kickoff` body as the tool result.
- WHEN the model invokes `hero_queue(limit?, horizon?)` via MCP THE SYSTEM SHALL return the ranked ready queue with kickoff bodies.
- WHEN the model invokes `hero_list(...)` via MCP THE SYSTEM SHALL return the filtered/sorted spec listing per the provided flags.
- THE SYSTEM SHALL implement all three MCP tools as read-only and route them through the same selector code as the CLI.

### Hygiene

- IF a non-completed spec has no `## Kickoff` section THEN `hero check` SHALL flag it and recommend re-running `/design` or hand-editing.
- WHERE a spec's `## Kickoff` "Pick up at:" line references AC items already marked completed THE SYSTEM SHALL surface an advisory drift notice in `hero check` (non-blocking).
- THE SYSTEM SHALL not introduce a model-call dependency in the pre-commit hook path.
- THE SYSTEM SHALL not project the queue into `.hero/NEXT.md` — NEXT.md remains the active-session handoff, QUEUE.md is the cold-start surface.

## Boundaries

- Does **not** federate the queue across repos. `cloud-mcp` is the right home for cross-repo surfacing.
- Does **not** rank by AI scoring. Heuristic signals + `pinned: true` are the only inputs.
- Does **not** project the queue into `.hero/NEXT.md`. NEXT.md is the single-session handoff; the queue lives in `.hero/QUEUE.md`.
- Does **not** add a `kickoff_tuned` / `kickoff_updated` frontmatter pair, an auto-refresh hook, or a `hero kickoff` parent command. The kickoff is part of the spec; skills and humans author it.
- Does **not** modify NEXT.md format — agent and machine halves stay as `agent-cold-start` and `pre-commit-auto-stage-next` defined them.
- Does **not** replace `/resume`, `/prime`, or `hero next show`. Composes with them — kickoff is the paste-in opener; those load deeper context once the session is alive.
- Does **not** persist kickoff history beyond `git log .hero/specs/<slug>/spec.md`.
- Does **not** add a daemon, watcher, or background refresh. The pre-commit hook plus explicit workflow invocations are the entire refresh surface for QUEUE.md.
- Does **not** make the pre-commit hook depend on a model call. `hero queue write` is a heuristic graph query — no LLM in the hot path.
- Does **not** touch the rest of the frontmatter schema beyond adding `pinned`. No reflow of existing fields.

## Mission Fit

> "Does this make the next agent session start smarter than the last one ended — and does it raise the floor for everyone, not just the senior dev who already knows what to ask?"

Yes — directly, on both axes.

**Smarter starts:** Today the user hand-crafts a session opener every time they switch tracks. Tomorrow they paste a 60–120 token block and the model is in the work. The kickoff captures the *delta* the spec body can't (current status, what to attempt next, files to open first), refreshed automatically.

**Floor-raising:** Today, "what should I work on?" requires knowing the project, the graph, and the right `hero` invocations. Tomorrow, `hero queue` is the answer — same data for a senior dogfooding the project and a brand-new clone whose owner just ran `hero scan`. The kickoff is the on-ramp.

This spec compounds the win from `agent-cold-start` (one path, one prompt) to *every* path, every session start, in proportion to how many parallel work streams the user is juggling — which is where the original problem actually lives.
