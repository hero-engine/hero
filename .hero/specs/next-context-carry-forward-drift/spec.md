# NEXT.md projection drift gate still unwinnable — carry-forward ranking uses volatile graph state

## Summary

### Categorization
| Attribute | Assessment |
|-----------|------------|
| **Criticality** | high — the `Test` workflow's "NEXT.md projection drift gate" fails on effectively every commit on every project, masking the real test signal and blocking clean releases. |
| **Ease of Fix** | easy — drop one volatile column (`ingested_at`) from two `ORDER BY` clauses in `internal/projection/projection.go` and add a committed-derivable tie-break. |
| **Caused by our codebase?** | Yes — the projection ranks two byte-gated sections on a graph-runtime timestamp that is not reproducible from committed sources. |
| **Needs more research?** | No — root cause confirmed against source and against the live working graph (query evidence below). |

### Background
This is the follow-up defect to the COMPLETED fix `next-drift-gate-unwinnable`. That fix removed three volatile elements from the byte-gated `.hero/NEXT.md` (the `updated:` timestamp — now `-I`-ignored by the gate; the churny size-drift COUNT — section removed; the dead `hero scan -q` flag — fixed). It MISSED a fourth volatile-by-construction section. The `## Context to carry forward` ranked list — and, latently, the `## Next` pick — order their results by `ingested_at DESC`, a wall-clock timestamp stamped when a node was last ingested into the graph. That value is graph-runtime state, not a function of committed `.hero/` sources, so it differs between the pre-commit hook's projection (dev's accumulated working graph) and CI's projection (clean rebuild). The byte-exact `git diff -I'^updated: ' -- .hero/NEXT.md` therefore still can't be empty.

### Analysis
The drift gate compares the committed NEXT.md against a freshly-projected copy. Two projection paths produce that file from two different graph states:
- **Pre-commit hook** (`.git/hooks/pre-commit`): runs `hero next checkpoint -q` against the developer's **existing working `graph.db`** — no `hero scan`. `ingested_at` on each node reflects when that dev last touched/re-ingested that spec across their session history.
- **CI gate** (`.github/workflows/test.yml`): runs `./hero scan` to rebuild `graph.db` fresh (it is gitignored), then `hero next checkpoint`. On a clean scan every node is inserted in one pass, so `ingested_at` collapses to ≈ the single scan wall-clock time for all nodes.

`ORDER BY ingested_at DESC LIMIT N` over those two states returns different rows, so the committed list and the CI-projected list diverge on at least one line, and the gate fails.

### Root Cause
`internal/projection/projection.go` ranks two byte-gated NEXT.md sections on `ingested_at`, a non-committed-derivable graph-runtime column:
1. `contextToCarry` (line ~300): `... ORDER BY ingested_at DESC LIMIT 5` — the `## Context to carry forward` list. **Primary, live defect.**
2. `openFeaturesByPriority` (line ~192): `... ORDER BY COALESCE(priority,'P9'), ingested_at DESC LIMIT ?` — the `## Next` pick. **Secondary, latent-but-live defect** (`ingested_at` is only the tie-break, so it bites whenever ≥2 features share the top priority — which is the normal case here: 39 open P0 features).

Compounding the divergence: `ingested_at` values arrive in huge same-second clusters (evidence: 100 Decision/Initiative nodes share one timestamp; all 39 P0 features share `2026-07-11T23:01:00Z`). With ties that large, `ORDER BY ingested_at DESC LIMIT 5` is decided by SQLite's implicit rowid (insertion/scan-order) tie-break — so the output is effectively **nondeterministic** across graph rebuilds even before the working-vs-clean divergence.

Because `UpsertNode` is content-hash idempotent (`internal/graph/node.go:155-166`), an unchanged spec keeps its old `ingested_at`; a touched spec gets `nowRFC3339()` (`node.go:87-89`). That is exactly what makes the working graph's ordering track "what this dev recently edited" while the clean scan's ordering tracks "scan iteration order" — two unrelated orderings.

### Source
- `internal/projection/projection.go` — `contextToCarry` and `openFeaturesByPriority` queries (the two `ORDER BY ... ingested_at` clauses).
- `internal/graph/node.go` — `UpsertNode` defaults `ingested_at` to `nowRFC3339()` and skips it on a content-hash match (why the column is volatile).
- `.git/hooks/pre-commit` (generated by `hero install` / `hero next install-hooks`) — projects from the working graph, does not scan.
- `.github/workflows/test.yml:43-64` — the gate: clean `hero scan` + `hero next checkpoint` + byte-diff.

### Fix Direction
Make every byte-gated NEXT.md section a pure function of committed `.hero/` sources. Concretely: purge `ingested_at` from the `ORDER BY` clauses of `contextToCarry` and `openFeaturesByPriority`, replacing it with a deterministic committed-derivable key (the node `key`/slug, optionally preceded by the committed `created` frontmatter date). This keeps the carry-forward context intact (handoff magic preserved) while making the hook's output byte-identical to CI's clean-scan output. It does **not** touch the gate's real purpose — a hook-less / stale commit still diverges on the stable content.

## Root Cause Analysis

**Confirmed.** Evidence:

1. **`ingested_at` is wall-clock at ingest, not committed-derivable.** `internal/graph/node.go:87-89`:
   ```go
   if n.IngestedAt == "" {
       n.IngestedAt = nowRFC3339()
   }
   ```
   And the upsert is content-hash idempotent (`node.go:155-166`): an unchanged node keeps its prior `ingested_at`; a changed/re-touched node gets a new one. So on a working graph `ingested_at` ≈ "when this dev last edited this spec"; on a clean scan it ≈ "scan time" for everything.

2. **Two byte-gated sections order on it** (`internal/projection/projection.go`):
   - `contextToCarry`: `ORDER BY ingested_at DESC LIMIT 5` (the `## Context to carry forward` list).
   - `openFeaturesByPriority`: `ORDER BY COALESCE(json_extract(props,'$.priority'),'P9'), ingested_at DESC LIMIT ?` (the `## Next` pick).

3. **Massive timestamp ties make it nondeterministic even within clean scans.** Live working-graph queries:
   - `Decision`/`Initiative` candidates: the current top cluster — `single-source-install`, `hero-ops`, `hero-ops-agents-and-skills`, … — all share `ingested_at = 2026-07-12T20:08:38Z`; a separate cluster of **100** nodes shares `2026-07-11T23:01:00Z`.
   - Open `Feature`s: **39 P0 features all share `2026-07-11T23:01:00Z`**. `## Next` (NextN=1) picks one of 39 tied rows by rowid — pure scan-order luck. Committed file currently shows `core-vertical-layering`; a clean scan in a different filesystem walk order can pick a different P0.
   - Committed carry-forward list (`single-source-install`, `hero-surface-deployment-and-rendering`, `cold-start-trust-hardening`, `concurrent-session-branching`, `environment-awareness`) already does **not** match the working graph's current top-5 — direct proof the ordering shifts under the same repo.

4. **Hook vs CI asymmetry is the trigger.** Hook projects from the working graph (no scan); CI projects from a clean scan. Even a perfectly deterministic `ingested_at`-free tie-break is required because the two graphs assign different `ingested_at` values and different rowids.

**Hypothesis vs confirmed:** The divergence mechanism (volatile `ingested_at` ordering + hook/CI asymmetry) is **confirmed** from source + live graph queries + the reported `--no-verify` reproduction. I did **not** re-run a full clean-scan-vs-hook byte-diff in this investigation (it would mutate the working `graph.db`); the validation section specifies that reproduction as the acceptance test. Given the code and the 39-way/100-way ties, the outcome is not in doubt.

## Suggested Fix Approach

Chosen direction: **(a) make the ranking deterministic from committed inputs only.** Rejected: (b) replacing the carry-forward list with a static pointer — it would gut the handoff value the section exists to provide (violates `feedback_handoff_magic_dont_break`); (c) making the pre-commit hook run `hero scan` — a full scan on every commit is too slow for a hook and still leaves the section nondeterministic under same-second `ingested_at` ties. (a) is the simplest correct fix, mirrors the prior fix's Direction-B philosophy (byte-gated NEXT.md must be deterministic from committed state), and preserves the section.

### Change 1 — `contextToCarry`: deterministic order (primary)
**File:** `internal/projection/projection.go`, function `contextToCarry` (~line 300).

**Before:**
```go
	rows, err := store.DB().Query(
		`SELECT type, key,
		        COALESCE(json_extract(props, '$.title'), key) AS title,
		        COALESCE(json_extract(props, '$.claimed_by'), '') AS claimed_by
		   FROM nodes
		  WHERE type IN ('Decision', 'Initiative')
		    AND repo = ? AND valid_to IS NULL
		    AND COALESCE(json_extract(props, '$.status'), '') NOT IN ('completed', 'superseded')
		  ORDER BY ingested_at DESC
		  LIMIT 5`,
		repoKey,
	)
```

**After:**
```go
	rows, err := store.DB().Query(
		`SELECT type, key,
		        COALESCE(json_extract(props, '$.title'), key) AS title,
		        COALESCE(json_extract(props, '$.claimed_by'), '') AS claimed_by
		   FROM nodes
		  WHERE type IN ('Decision', 'Initiative')
		    AND repo = ? AND valid_to IS NULL
		    AND COALESCE(json_extract(props, '$.status'), '') NOT IN ('completed', 'superseded')
		  ORDER BY COALESCE(json_extract(props, '$.priority'), 'P9') ASC,
		           COALESCE(json_extract(props, '$.created'), '') DESC,
		           key ASC
		  LIMIT 5`,
		repoKey,
	)
```

**Why:** `priority` (committed frontmatter) is the primary signal; `created` (committed frontmatter, ISO date) breaks priority ties by newest-first — a meaningful, committed-derivable proxy for "recent context" that replaces the volatile `ingested_at`; `key` is the guaranteed-unique final tie-break so the order is total and identical between the working graph and a clean scan. `ingested_at` (graph-runtime) is gone from the byte-gated output. If keeping `priority`/`created` is judged to add scope, the minimal correct form is `ORDER BY key ASC` alone — still fully deterministic — but the priority-first form preserves more of the "most-relevant-first" intent.

### Change 2 — `openFeaturesByPriority`: deterministic tie-break (secondary, required)
**File:** `internal/projection/projection.go`, function `openFeaturesByPriority` (~line 192).

**Before:**
```go
		  ORDER BY COALESCE(json_extract(props, '$.priority'), 'P9'),
		           ingested_at DESC
		  LIMIT ?`,
```

**After:**
```go
		  ORDER BY COALESCE(json_extract(props, '$.priority'), 'P9') ASC,
		           COALESCE(json_extract(props, '$.created'), '') DESC,
		           key ASC
		  LIMIT ?`,
```

**Why:** Same fix, same reasoning: priority stays the primary sort; `created DESC` then `key ASC` give a deterministic, committed-derivable tie-break so the `## Next` pick is byte-identical across the two projection paths even with 39 features tied at P0. Without this, the gate stays flappy on `## Next` the moment scan order shifts.

### Change 3 (optional, insurance) — `attemptsForSession`
**File:** `internal/projection/projection.go`, function `attemptsForSession` (~line 264).
Leave `ORDER BY a.ingested_at` if it is judged out of scope (it is session-filtered and empty in the committed/CI path). If touched, order by a stable per-attempt key (e.g. `a.key`) instead. Recommend deferring unless a session-anchored NEXT.md is ever committed.

### Change 4 — gate purpose preserved (no code change, verify)
Confirm the existing negative test still holds: a stale/hook-less NEXT.md (managed region not regenerated) still diverges on the stable content and fails the gate. The two `ORDER BY` changes only make correctly-projected files converge; they do not weaken drift detection (mirrors prior-fix AC-4).
