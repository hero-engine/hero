## Goal

Refactor Hero's engineering-specific content (agents, commands, skills)
into a domain pack so other domains can be added without forking the
codebase. The core engine stays unchanged; domain packs are swappable
content directories.

## Kickoff

Foundation primitive for `hero-domains`. Pure refactor — move existing engineering content into `domains/engineering/` and add `hero init --domain` / `hero domain switch` plumbing. Zero new behavior, but unblocks every other primitive and every future domain pack (PM, QA, design, etc).

**Status:** planning — design exists from 2026-04-25; reframed as the foundation for the PM-first roadmap on 2026-05-15. No code written yet.

**Pick up at:** `/deliver` this spec. Examples below have been updated from sales-first to PM-first to reflect the current sequencing, but the actual refactor is content-agnostic — PM-specific pack content lives in the separate `hero-pm` spec.

→ `/deliver domain-plugin-architecture`

## Problem

Today, agents/, commands/, and skills/ are baked into the root of the
repo and the embedded filesystem. There's no concept of "this is
engineering-specific content." Adding a non-engineering domain (PM,
QA, etc.) would mean either forking the repo or cramming domain content
alongside engineering content.

## Design

### Directory restructure

Move the existing content into `domains/engineering/`:

```
domains/
  engineering/
    agents/           # moved from ./agents/
    commands/         # moved from ./commands/
    skills/           # moved from ./skills/
    AGENTS.md         # moved from ./AGENTS.md
    integrations.json # tracker config schema
```

The root-level `agents/`, `commands/`, `skills/`, and `AGENTS.md`
become symlinks or are generated by `hero install` from the active domain.

### Embedded filesystem update

`embed.go` currently embeds `agents/`, `commands/`, `skills/`. Update
to embed `domains/*/` and select the right one at install time based
on `hero.json` domain setting.

### hero init --domain

```bash
hero init                        # defaults to --domain engineering
hero init --domain pm            # uses domains/pm/ content
```

Writes `"domain": "<name>"` into `hero.json`.

### hero domain command

```bash
hero domain                      # show current domain
hero domain list                 # list available domains
hero domain switch <name>        # switch domain (re-installs content)
```

`hero domain switch` runs `hero install` with the new domain's content,
overwriting agents/commands/skills in the project. Preserves `.hero/`
data (specs, knowledge, jobs).

### hero install update

`hero install` reads the domain from `hero.json` and copies content
from the matching domain pack. If no domain is set, defaults to
engineering.

### Backward compatibility

- Projects without a `"domain"` key in hero.json default to engineering
- The embedded filesystem includes engineering as the fallback
- No data migration needed — only the content layer changes

## Changes

- `domains/engineering/agents/` — move from `./agents/`
- `domains/engineering/commands/` — move from `./commands/`
- `domains/engineering/skills/` — move from `./skills/`
- `domains/engineering/AGENTS.md` — move from `./AGENTS.md`
- `embed.go` — update embed directives to include `domains/`
- `internal/install/install.go` — read domain from config, select content
- `internal/cli/init.go` — add `--domain` flag
- `internal/cli/domain.go` — new `hero domain` command
- `internal/config/config.go` — add `Domain` field
- `internal/cli/root.go` — register domainCmd

## Acceptance Criteria

- WHEN `hero init --domain engineering` runs THE SYSTEM SHALL create a workspace with engineering agents, commands, and skills
- WHEN `hero init --domain pm` runs and a PM domain pack exists THE SYSTEM SHALL create a workspace with PM agents, commands, and skills
- WHEN `hero init` runs without `--domain` THE SYSTEM SHALL default to the engineering domain
- WHEN `hero domain list` runs THE SYSTEM SHALL list all available domain packs in the embedded filesystem
- WHEN `hero domain switch pm` runs THE SYSTEM SHALL reinstall content from the PM domain pack while preserving .hero/ data
- WHEN a project has no `domain` key in hero.json THE SYSTEM SHALL behave identically to the engineering domain
- THE SYSTEM SHALL embed all domain packs in the single hero binary

## Boundaries

- Does **not** support third-party domain packs loaded from disk (future)
- Does **not** migrate specs between domains (types are domain-specific)
- Does **not** change the core engine or internal packages
- Does **not** support running multiple domains in one workspace

## Decision — ContentFS legacy fallback retained (B1, 2026-05-17)

`ContentFS()` continues to return `legacyContent` (root-level `agents/`, `commands/`, `skills/`) rather than being cut over to `domains/engineering/`. Reasons:

1. The root-level dirs are still the actively-maintained engineering source; `domains/engineering/` is a scaffolded mirror per the existing `legacyContent` comment.
2. A clean cutover requires first syncing root → `domains/engineering/` so the two surfaces match bit-for-bit. That sync is out of B1 scope (B1 is the embed.FS cutover for PM, not an engineering content migration).
3. `DomainFS("engineering")` already returns `legacyContent`, so the domain-pack interface is consistent — callers that go through `DomainFS` get the same content regardless of how the root is wired.

Removing the legacy fallback is deferred to a follow-up that (a) reconciles root vs `domains/engineering/`, (b) switches the `legacyContent` embed to `domains/engineering/...`, and (c) drops the root-level dirs (or makes them generated artifacts of the install step). Until then, both surfaces are kept in lockstep by the engineering vertical being the single source of truth for both.
