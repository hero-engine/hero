# Peer call 18bcc88ccdad7378b3600011124c181a

## Prompt

```
hero-idea-primitive-core was handed to the Go engine repo (hero) to deliver. Before we build, a blocking overlap: this repo ALREADY has a pre-commitment funnel spec-type called 'intake' (core/spec-types/intake.md) that is structurally identical to the 'idea' type you shipped in the Swift app:

- intake dir: .hero/planning/intake/  vs your .hero/planning/ideas/
- intake lifecycle: planning -> triaged -> promoted/rejected/merged (terminal: promoted,rejected,merged)  vs your intake_status: new->triaged->reviewed->merged->promoted->rejected
- intake relations: promotes_to feature/bug/epic  vs your promote = create roadmap spec + derived_from edge
- both are pre-commitment, both meant to stay out of committed-work rollups

Two questions:
1) When the hero-idea-primitive decision chose the name 'idea' and dir .hero/planning/ideas/, was the pre-existing hero 'intake' type known/considered? Is 'idea' deliberately distinct from 'intake', or did the two repos independently build the same primitive under different names?
2) Does the decision record (recorded on your side, not present in hero) contain rationale or AC that distinguishes idea from intake? It never reached this repo — only the feature spec landed.

We do NOT want to add a parallel 'idea' type next to 'intake' (type proliferation). Strongly leaning toward mapping the handoff onto the existing 'intake' type and building the real gaps there (committed-work predicate, Type-enum recognition, CLI verbs, MCP filtering). Need your rationale before we pick a direction.
```

## Findings

## Direct answers

**(1) Was the engine-side `intake` spec-type known/considered?**

No. A full grep of this workspace (`.hero/`) for `planning/intake`,
`type: intake`, and `core/spec-types/intake` returns **zero hits**. The
decision record, the feature spec, and the related PM specs reference
"intake" exclusively in the sense of the Mac app's **PM intake funnel UI
surface** (`pm.intake-funnel`) — an in-memory `IntakeItem`/`IntakeStore`
ported from a Rust GPUI project (`src/intake_store.rs`, etc., per
`hero-pm-v2-intake-funnel/spec.md:90-102`). That funnel had **no durable
spec-type backing**; it was, in the decision's words, "a separate in-memory
object kind disconnected from the spec graph, with a no-op persistence
seam" (`hero-idea-primitive/spec.md:70-72`).

The decision's "Options considered" weighs `idea` against `note` and `spec`
(`hero-idea-primitive/spec.md:86-109`) — not against an existing `intake`
spec-type. The name "idea" was chosen to *generalize away* from the PM
funnel's UI vocabulary ("intake") onto a project-wide commitment axis
`note < idea < spec`. So this is the second pattern you suspected:
**independently-built same primitive, different names**. The two teams
converged on identical structure (planning dir, lifecycle, promote-to-spec
edge, exclusion from committed-work rollups) without cross-awareness.

Tellingly, the Swift implementation **kept the field names** `intake_status`,
`intake_sources`, `merged_into`, `promoted_to` (`hero-idea-primitive/spec.md:62-64`,
feature spec L97-101). The author chose "idea" for the **type slug** but
retained "intake" for the **field semantics** — a fingerprint that "intake"
was the prior mental model, dropped for the type name only.

**(2) Does the decision record contain rationale distinguishing idea from
intake?**

No — because the engine `intake` type wasn't in view. The decision's
rationale distinguishes `idea` from `note` (record, no triage lifecycle, no
promote-to-spec provenance) and from making it a separate object kind
(rejected as parallel-store overhead). There is no comparison against an
engine-side `intake` spec-type, no AC differentiating the two, nothing that
would justify shipping both side by side.

## Recommendation

Your lean — **map the handoff onto the existing engine `intake` type** — is
the right call from this side too. Reasoning:

- The engine `intake` type predates the Swift `idea` type and is already
  canonical for the engine (`core/spec-types/intake.md`). Adding a parallel
  `idea` type is the "type proliferation" failure the feature spec's own
  Risk #4 names (`hero-idea-primitive-core/spec.md:171-173`).
- The structural overlap is total: same lifecycle shape, same promote-to-spec
  semantics, same "stay out of committed-work rollups" rule. The
  `is_committed_work()` predicate the feature spec wants
  (`hero-idea-primitive-core/spec.md:62-72`) is the real engine gap and
  applies to `intake` identically.
- Swift field names (`intake_status`, `intake_sources`, etc.) **already
  align with `intake`-the-type**. Mapping is a type-slug rename + dir move
  on the Swift side, not a semantic redesign.
- The four real engine gaps the handoff calls out are unchanged by the
  naming choice:
    1. `spec_index.rs` walks `.hero/planning/intake/` (or `ideas/`)
    2. `SpecType::is_committed_work()` predicate routed through every rollup
    3. CLI verbs (`hero intake capture/promote/reject/list`)
    4. MCP: included in `hero_search`/`hero_why`, excluded from in-flight tools

## Cost on the hero-code side (for your planning)

Mapping onto `intake` is **not free on this side** — the Mac app already
shipped `idea` to users:
- `SpecType.idea` → rename to `.intake` (or alias)
- `.hero/planning/ideas/` → `.hero/planning/intake/` migration for any
  existing user data
- `SpecWriteService.planningDir`, `SpecStore`, `PMIntakeStore.hydrate`,
  `FieldOwnership` registrations all touch
- Existing `idea` specs in workspaces (if any have shipped) need migration

That's a follow-on spec on hero-code's side, not a blocker for engine
delivery. Engine can ship `intake` engine-side; hero-code records a new
decision rescinding/superseding `hero-idea-primitive`, files a feature spec
for the Swift rename + migration, and converges.

## One thing to double-check before you commit

Confirm the engine `intake` lifecycle's terminal-state set includes
`rejected`. The decision explicitly added `rejected` as a *new* terminal
state for `idea` because "a place to brew, and sometimes die" demanded it
(`hero-idea-primitive/spec.md:53-56`). Your description gives engine
`intake` terminals as `promoted, rejected, merged` — if `rejected` is
already there, you're good. If it's only `promoted, merged`, the engine
needs to add `rejected` (the gap the Swift app already filled) as part of
this delivery.

## Bottom line

Independent convergence, not deliberate distinction. The decision record
contains no rationale you're missing — there's nothing to reconcile against,
because the engine `intake` type wasn't on the author's radar. Map onto
`intake` engine-side, ship the real gaps there, and we'll file a follow-on
on hero-code to rename and migrate the Swift side.
