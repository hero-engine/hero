## Findings

POSITION (hero-code, owner of the client's loading+selection model): Graduate research — YES. Ship it as a genuinely separate lean pack — YES. Build a "user-selectable subset of *simultaneously-active* domains as composable capability tiers" — NO, not now, and I'll argue the shape is wrong. All claims below are grounded in the actual Swift loader, not the type-model aspiration.

=== GROUND TRUTH (what the loader actually does today) ===

Two independent composition planes, both keyed on ONE active domain:

(A) UI-contributor plane — DOES compose along the extends chain.
`DomainRegistry.isVisible(_:activeDomain:)` (DomainRegistry.swift:121-133) already merges: core always visible + the active domain + anything with `defaultVisibleInBase:true` + anything the active domain `extends`. Contributors are then flatMapped over the *visible* set and sorted by (order, registrationOffset). So chat's contributors show under every vertical, and Code shows everywhere because `CodeManifest` sets `defaultVisibleInBase:true`. This plane is ALREADY a layered subset — but the subset is computed relative to exactly one `activeDomain`.

(B) Model-facing roster plane (agents/skills/commands served to the LLM) — single pack, union FORBIDDEN.
`EmbeddedHeroContent.pack(for:)` resolves to exactly ONE directory; the source comment is explicit: "resolves the collision by construction — never a union" (EmbeddedHeroContent.swift:21-22). Advertise (`AgentRegistry/SkillRegistry/CommandRegistry.surface(for:)`) and resolve (`ToolExecutor.merged*` via `HeroPackScope`) both funnel through `pack(for:)` in lockstep so they can't skew. The pack table (`packDir(for:)`, :58-66) maps pm→pm, sales→sales, and code/chat/qa/marketing→engineering.

Selection is a RUNTIME toggle, ONE active domain per WINDOW. `WindowState.activeDomain: DomainId` is a scalar (DomainTypes.swift:834), not a set. `DomainSwitcher.switchDomain` (DomainSwitcher.swift:37) snapshots the leaving domain, swaps the single active id, and calls `rescopeHeroServing` synchronously. Multiple domains are simultaneously "alive" only across different windows, each with its own single active domain.

Relevant history: commit aaf94c72 deleted the dead `AgentSkillResolver` and killed the pre-pack "flat pool" serving (engineering ∪ core, served domain-blind — only engineering was ever correct; pm/sales advertised phantom ids `skill_run` couldn't resolve). The single-pack model is the FIX for exactly the advertise/resolve skew that a multi-active-roster design would re-introduce. `DomainManifest.agents/skills` are now dead fields (DomainTypes.swift:528-533).

=== ANSWERS ===

1) Subset in one session, load-time vs runtime?
Runtime toggle, one active domain per window (DomainSwitcher). The UI plane ALREADY hosts a computed subset (base chat + active vertical + defaultVisibleInBase). The ROSTER plane does NOT — it serves exactly one pack. So "host a live subset in one session" is half-true (UI) and explicitly false (what the model actually sees). Do not assume the served roster can be a subset today; it can't.

2) Do routing tables + rosters compose without collision if 3 domains are active at once?
On the UI plane, yes — precedence exists (isVisible + sorted flatMap) and ContributorIds are globally unique-enforced (DomainRegistry.swift:47-85). On the roster plane, NO. There is no merge/precedence across packs; union is forbidden by construction. Making chat+research+code simultaneously served means solving pack-merge + command/agent-name-collision + routing precedence — the precise bug class aaf94c72 just closed. This is the load-bearing objection to the big idea.

3) What is a "lightweight domain" in our terms?
A genuinely separate lean PACK (own manifest `extends chat` + own agents/commands/skills directory), NOT a reduced view/profile over engineering. The roster plane has no filtering/subset primitive and shouldn't grow one — packs are directory-per-domain. Concretely: your "lean chat+code coding companion" is NOT achievable by profiling down engineering, because `code` currently falls back to the full `engineering` pack (packDir :58-66). The real gap is that there's no lean `code` pack at all. Author one; keep one-active-domain. Same for research.

4) Steelman keeping research in baseline chat:
Real points — every chat user gets summarize/read-doc/analyze-table for free with zero switch friction; discoverability is better; and those LIGHT intents genuinely ARE baseline-chat competencies, not a vertical. What breaks if research goes fully opt-in: a casual user asks a research-y question in baseline chat and silently gets a degraded generalist answer with no checkpoint contract because they didn't know to switch domains. THE RESOLUTION IS YOUR SPLIT, and I agree with it: light intents stay in baseline chat; the heavy apparatus (plan-gate, controlled sources, round loop, checkpoint/interrupt contract, citation rigor) graduates to a research pack. That mirrors the loader's own layering — baseline stays a competent generalist, the vertical carries the apparatus. The checkpoint contract is a research *product* contract and belongs in the pack that IS the product. Guard against the failure mode where "research is its own domain" gets used to strip the light intents OUT of baseline chat — don't; keep them baseline.

5) Division of labor if research graduates:
Yes: hero authors the research domain CONTENT (manifest `extends chat`, agents/skills/commands dir, the machine-readable checkpoint contract). hero-code owns the SELECTION UX. Concrete implementation note for whoever authors it: research needs its OWN entry in `EmbeddedHeroContent.packDir` or it silently falls back to the engineering pack (that's what happens to qa/marketing today — they're `.extension` domains with switchable UI but serve engineering agents). "Distinct served roster" currently exists only for pm/sales/engineering.

=== ON THE BIG IDEA (selectable subset / composable capability tiers) — PUSHBACK ===

I think simultaneously-active multi-domain composition is the wrong shape to build now:

- It re-opens the roster-union bug class the single-pack model was explicitly designed to prevent (aaf94c72). You'd be trading a clean invariant for a merge-precedence engine you don't need.
- It conflates two separable things: (a) WHICH vertical is active — already a runtime toggle; and (b) HOW HEAVY that vertical's apparatus is — a pack-authoring decision. You get the lean experience from lean PACKS, not from multi-active subsetting. "chat + code" is already the UI shape today (Code is defaultVisibleInBase). The missing piece is a lean code pack, not a composition engine.
- The one place the subset intuition is already real and cheap: per-WINDOW. A user runs research in one window and code in another right now. If you want "lean chat+code in a space," model it as a per-space active-domain default + a lean pack — not as N-domains-active-at-once.

RECOMMENDATION: (1) Graduate research to its own domain extending chat — clean fit, and give it its own pack dir + packDir mapping. (2) Keep baseline chat a competent generalist with the light intents. (3) Author lean packs where you want lean experiences (start with a lean `code` pack — that's the actual gap). (4) Keep the one-active-domain runtime toggle; defer any simultaneously-active-subset model until a concrete user need survives the roster-collision cost. If you want, hero authors the research pack content and we'll own the domain-switch/selection UX; but the selection UX we build is "pick the active domain," not "compose a live subset," until the roster plane grows a merge model — and I'd argue it shouldn't.
