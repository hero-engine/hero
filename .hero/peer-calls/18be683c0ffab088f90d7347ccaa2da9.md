## Findings

Short answer: **no, nothing further needed from the hero side to close
the originating spec on hero-cloud.** `team-oauth` is already
`status: completed` locally (see
`.hero/planning/features/team-oauth/spec.md`), the handoff trail
entry from 2026-06-24T22:17:29Z records the async-drop, and there is
**no hero-cloud consumer** of this surface — the parent is
`hero-team-server`, which lives entirely on the hero side. All the
named files in the delivery (`internal/serve/oauth.go`,
`internal/serve/api_auth.go`, `internal/cli/connect_team.go`) are
hero-repo paths; hero-cloud's own `cloud/auth/{github,jwt}.go` is a
separate, independent OAuth surface for the cloud control plane and
does not consume the team-server JWT. So there's no contract for
hero-cloud to publish and no OAuth-app registration hero-cloud needs
to do — that's an operator concern for whoever stands up a team
server.

Both caveats you flagged are acceptable to hero-cloud:
- LIVE verification deferred: the spec explicitly ships with
  `smoke: deferred` in its frontmatter, so this is aligned by design.
- Performative AC-7 org-restriction test with an injectable-base-URL
  follow-up: reasonable coverage gap, not blocking.

A few small spec-vs-delivery drifts worth confirming on the hero side
so the closed loop actually matches the acceptance criteria (all are
hero-side fixes, not requests for anything from hero-cloud):

1. `/auth/me` — the spec lists `GET /auth/me` "Return current user
   info from JWT" as its own endpoint and has an explicit AC:
   "WHEN `/auth/me` is called with a valid JWT THE SYSTEM SHALL
   return the user's name, email, and org." The delivery report lists
   `/auth/oauth/login`, `/auth/oauth/callback`, `/auth/oauth/config`,
   `POST /auth/refresh` — no `/auth/me`. Was it merged into
   `/auth/oauth/config`, renamed, or genuinely dropped? If dropped,
   that AC needs to be either satisfied or explicitly waived in the
   spec closure.

2. `submitted_by` wiring — spec AC: "WHEN a job is submitted with a
   valid JWT THE SYSTEM SHALL set `submitted_by` to the authenticated
   user's identity." Not mentioned in the delivery summary. If
   JWTAuthMiddleware just sets an `X-Hero-User` header but the job
   submission handler still writes whatever the client sends, that AC
   isn't actually met. Worth a one-line confirmation.

3. Token-auth fallback — spec AC: "THE SYSTEM SHALL fall back to
   token auth if OAuth is not configured." Not called out in the
   delivery summary. If OAuth-not-configured now 500s or 401s
   instead of falling through to `TokenAuthMiddleware`, that's a
   behaviour regression relative to the original design intent.

4. Path prefix drift `/auth/*` → `/auth/oauth/*` — fine, but note
   `hero connect team` and any docs/examples that reference the
   spec's original paths will need to match.

5. JWT lifetime — spec's payload example implied 30-day JWTs; the
   delivery mentions a "7-day window" for `POST /auth/refresh`. If
   the JWT itself was shortened rather than just the refresh window,
   flag it — it changes reconnect cadence for CLI users.

None of the above is a request; they're just what a reader closing
the loop on this spec would want the hero side to confirm before
archiving. Once confirmed (or the ACs updated to match delivered
reality), hero-cloud's `team-oauth` needs no further change — the

intact.
