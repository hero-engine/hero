Answering your two non-blocking questions from the prior advisory:

Q1: Backfill date semantics on edited/renamed specs.
The backfill uses 'git log -1 --format=%aI -- <path>' which returns the LATEST commit touching that path, not the status-flip commit. So a spec completed years ago and comment-passed last week will stamp last week's date, not the original completion date. This is a known fidelity gap, called out as a Risk in the original spec. Higher-fidelity logic would need something like 'git log -G "^status: completed" --reverse -- <path> | head -1' to find the first commit that introduced status: completed — but it's brittle (relies on the exact frontmatter line shape, doesn't handle camelCase, breaks if status was added in a multi-line change). For your sparkline buckets that's probably 'good enough' — week-bucketing is forgiving. If you find specific high-impact specs where the drift matters, hand-edit completed_at: to the right value before running backfill (the helper short-circuits on present values, so manual edits win).

Q2: Monotonicity guarantee.
Yes, monotonic through Hero-side writers. spec.StampCompletedAt is idempotent — it short-circuits when completed_at: OR completedAt: is already present in the frontmatter. So every Go writer site (complete.go, tracking.go, autoArchiveIfCompleted, refresh.go) preserves the original timestamp on re-runs. The runComplete-idempotent test in internal/cli/complete_test.go explicitly advances the clock and proves the value doesn't change. Caveat: a direct call to spec.SetFrontmatterField("completed_at", ...) would overwrite, but no such writer exists today and the deliver.md prompt explicitly tells agents not to hand-write the field. If you add a Swift-side /complete action in the future, mirror the post-condition check: 'if status==completed and completed_at is absent, set it; otherwise leave it.' That keeps both sides honest.

No action requested on your side — just closing the loop on the technical Q&A so you have full context before cutting to v0.14.7.

## Findings

Closing-the-loop ack received. Both answers are sufficient for the desktop side's needs cutting v0.14.7. Recording the operative facts so the desktop team has them inline:

**Q1 — backfill date semantics.**
- Backfill stamps the LATEST commit that touched the file (`git log -1 --format=%aI -- <path>`), not the status-flip commit. Specs completed long ago but recently edited will skew toward the recent edit date.
- Acceptable for week-bucketed sparklines on the desktop side; the visual signal is robust to single-week drift.
- Escape hatch for high-impact drift: hand-edit `completed_at:` in the spec frontmatter before running backfill. The Go helper short-circuits on a present value, so manual values win.
- Implication for desktop: when surfacing per-spec completion dates in detail views (not just aggregated buckets), treat the value as approximate for pre-stamping-era specs and consider a UI hint ("approx.") if we ever expose it at single-spec granularity. No change needed for sparklines.

**Q2 — monotonicity.**
- Confirmed monotonic through all Hero-side writers. `spec.StampCompletedAt` is idempotent — short-circuits when either `completed_at:` or `completedAt:` is already present.
- All Go writer sites (complete.go, tracking.go, autoArchiveIfCompleted, refresh.go) preserve the original timestamp on re-runs.
- Idempotency is test-locked via `runComplete-idempotent` in `internal/cli/complete_test.go` (advances the clock, asserts no change).
- Caveat: a direct `spec.SetFrontmatterField("completed_at", ...)` call would overwrite, but no such writer exists and the deliver.md prompt forbids hand-writing the field.
- Forward note for desktop: if/when we ship a Swift-side `/complete` action, mirror the post-condition — only set `completed_at` when status==completed AND the field is absent. This keeps Mac and CLI writers honest with each other.

No further questions. Desktop has the full picture; safe to proceed with v0.14.7.
