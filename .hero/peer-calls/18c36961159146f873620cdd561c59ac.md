## Findings

Scope note first: "hero-code" here is the Rust core (crates/hero-core) that
bundles + loads Hero content. The chat *rendering* surface (plan-approval UI,
per-checkpoint progress, stop control) is NOT in this repo — it lives in the
SwiftUI client (hero-chat-swift-app). So I can answer (1) authoritatively from
the loader code, and (2) I can flag the contract-shape risks the client has to
absorb, but I can't inspect the client's renderer from here.

(1) CAN hero-code load the new agent/skill surface as-is? YES — confirmed, no
code change needed on our side.
- Loading is fully dynamic directory-iteration, not a hardcoded roster.
  crates/hero-core/src/hero/embedded.rs::load_all_for(domain) walks
  EMBEDDED.get_dir(domain) over [Agents, Skills, Commands] and turns every
  file into a ContentItem (Status::Active), keyed by frontmatter `name` (falls
  back to file stem). New files under domains/chat/{agents,skills,commands}/
  are picked up automatically once the binary is rebuilt with the staged
  OUT_DIR tree. Your build.rs verification (3 agents + 5 skills + 7 commands
  under hero-content/chat/) is exactly what our include_dir! bakes in.
- registry.rs loads the domain-scoped roster via embedded::load_all_for(domain)
  and the chat domain sees ONLY its own bundled content (there's an existing
  test asserting the chat roster never leaks engineering commands like
  /design). /research will surface as a chat command; the 3 agents become
  active_agents(); the 5 skills become active_skills(). No AvailableDomains /
  go:embed analog on our side — agreed, nothing changes.
- One conformance gotcha, not a blocker: every agent ContentItem must have
  non-empty `description` frontmatter, else registry.rs emits a
  "model won't know what it's for" warning and the agent renders as
  "(no description)". Please confirm researcher / document-analyst /
  data-analyst each carry a description. They'll still load either way.

(2) Checkpoint/interrupt contract — where it does NOT map cleanly:
- THERE IS NO STRUCTURED CHECKPOINT/INTERRUPT TYPE ANYWHERE IN HERO-CORE.
  grep across the Rust source: "checkpoint" appears only in an unrelated
  preamble .md and a file-parse module; "interrupt" appears nowhere. The
  plan->round(xN)->evaluation->synthesis->report sequence, the plan-BLOCKS-on-
  approval gate, and the 'Incomplete - stopped after round K' banner are all
  PROSE inside research-workflow/SKILL.md. We bundle that body verbatim and
  feed it to the model; we emit no typed "checkpoint reached" / "awaiting plan
  approval" / "interrupted" event. Consequence for the client: plan-approval
  blocking, per-checkpoint progress, and the interrupt banner must be inferred
  from model output text (marker-string sniffing), not read off a structured
  signal. That's the single biggest mapping risk — a contract carried in
  natural language has no schema the SwiftUI renderer can bind to, so any
  wording drift in the skill silently breaks the client's detection.
  Recommendation to close it cleanly: define a small machine-readable emission
  (e.g. a fenced sentinel line per checkpoint, like Hero's peer-call
  <...-result> fence) that the researcher MUST print at each transition, and
  make the 'Incomplete - stopped after round K' banner the FIRST-LINE contract
  it already is. First-line + fixed-prefix is parseable; free-prose is not.
- The 'plan' checkpoint "BLOCKS on user approval before any search runs" is a
  behavioral instruction to the model, with no enforcement floor on our side.
  If a model ignores it and searches anyway, nothing in hero-core stops it —
  same class of issue we already know from Hero workflows being narrated rather
  than executed. The client should treat plan-approval as advisory-enforced and
  ideally gate tool execution itself rather than trusting the model to pause.
- Interrupt/stop: hero-core does not own the agent loop for the chat surface,
  so the stop control + partial-report emission live in the client's loop.
  The contract (emit a usable partial whose first line is the banner) is sound
  IF the client's cancel path lets the model produce one final assistant turn
  after the stop signal rather than hard-killing the stream mid-token. Flag to
  hero-chat-swift-app: verify the stop button requests a graceful wind-down
  (one more turn to emit the banner+partial), not an immediate socket close —
  otherwise the "never a dropped turn" guarantee can't hold.
- Minor: "hidden" skills. hero-core has no `hidden` frontmatter concept.
  Skills are simply Category::Skills, a different bucket than Category::Commands,
  so they never surface as slash commands regardless — functionally correct.
  But if the client's roster/settings UI lists active_skills(), all 5 appear as
  normal skills with no hidden flag to suppress them. If "hidden" is meant to
  keep them out of a user-facing list, that suppression has to be a client-side
  convention (or a new frontmatter field we'd both honor); today it's a no-op
  on our side.

Net: loading is a clean yes, zero changes needed. The gap is entirely in the
contract's SHAPE — it's prose, not a typed event stream — which pushes all
checkpoint/interrupt detection onto the client as string-matching. Worth a
tiny structured emission contract before the SwiftUI surface hard-codes marker
sniffing.
