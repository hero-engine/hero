## Findings

SHORT ANSWER
In the hero-code desktop app, chat mode does NOT render domains/chat/AGENTS.md
into the model's instructions. There IS a live "Hero instructions" layer that
injects a domain pack's AGENTS.md body into the system prompt — but for chat it
resolves to the ENGINEERING pack's AGENTS.md, not chat's. The chat pack is never
even extracted into the app. So authoring ambient habits in domains/chat/AGENTS.md
is decorative *as far as this app is concerned* today. Two independent reasons,
both below.

── Q1: Is domains/chat/AGENTS.md in chat mode's system prompt? ──
No. But the mechanism you're hoping for exists and is real — it just doesn't
point at the chat pack.

The lever: ProjectContext.buildSystemPromptWithLayers (…/Engine/ProjectContext.swift)
emits an always-present "Hero instructions" layer, source-labelled
"generated · <domain> pack AGENTS.md", whose content is literally
EmbeddedHeroContent.pack(for: activeDomain).agentsMD — the pack's raw AGENTS.md
body (H1 + ### sections). This landed as commit 0de7a6af ("domain-scoped Hero
instructions layer (AC10)"): it's independent of project memory, so a project
CLAUDE.md no longer suppresses it, and it swaps on domain switch. So per-domain
AGENTS.md bodies genuinely DO reach the model. Your README ("the app serves
AGENTS.md") is correct — for the domains that are actually served.

Why chat's specifically does NOT reach it — two gates, either one is fatal:

1. Chat is never extracted. scripts/extract-hero-content.sh builds
   Resources/hero-content/ by enumerating `hero domain list` off the hero binary
   and copying {agents,commands,skills,AGENTS.md} per domain. Its own header
   comment says: "hero's `chat` pack is deliberately not in that list (it has no
   go:embed directive; see hero's content.go), so it is absent here rather than
   fabricated." On disk we have exactly three domain trees: engineering, pm, sales.
   No chat tree, no chat AGENTS.md, no chat commands.

2. Even the DomainId→pack mapping routes chat away. EmbeddedHeroContent.packDir(for:)
   maps code/chat/qa/marketing → the "engineering" fallback pack. And chat mode's
   activeDomain literally defaults to DomainId("chat") (AppState.swift:917), which
   is passed straight into buildSystemPromptWithLayers. So chat sessions get the
   ENGINEERING pack's AGENTS.md as their "Hero instructions" layer.

Note on your premise: the "build.rs stages only agents/skills/commands, not the
top-level AGENTS.md" belief is outdated on our side. We have no build.rs for this —
it's a shell extraction (extract-hero-content.sh) run by `make build`, and it DOES
stage per-domain AGENTS.md, and that AGENTS.md IS consumed via the layer above. The
real gap is narrower and more specific: chat is not a served pack at all, so nothing
under domains/chat/* reaches the model here.

── Q2: Is wiring chat's AGENTS.md into chat-mode instructions the intended path? ──
Yes — that layer is exactly the right vehicle for ambient habits (cite sources,
don't fabricate, look things up, read what's shared). It is NOT that ambient behavior
is expected to live only in our client-side system prompt. Our client-side layer
(buildCorePreamble) carries generic harness behavior; the pack AGENTS.md body is the
intended channel for domain-flavored operating habits, and it already works for
engineering/pm/sales. So authoring them in AGENTS.md is the correct design — it's just
inert for chat until chat becomes a first-class served pack.

To make chat's AGENTS.md actually land, it takes changes on BOTH sides, and yours
is the upstream blocker:
  • hero (your side): give the chat pack a go:embed directive so `hero domain list`
    includes it. Our extraction is faithful to that list by design and will not
    fabricate a pack that hero won't enumerate. This is gate #1 and it's on you.
  • hero-code (our side): once chat is extractable, change packDir(for:) so "chat" →
    "chat" instead of the engineering fallback (a one-line mapping edit). Then the
    "Hero instructions" layer in chat mode injects domains/chat/AGENTS.md verbatim.
Until BOTH land, chat inherits engineering's AGENTS.md, and the soft citation
convention / research habits in domains/chat/AGENTS.md have zero runtime effect in
this app.

── Q3: Does the commands-only trim flow through cleanly? ──
The extraction/serving mechanism is generic per-category — CommandRegistry,
AgentRegistry, SkillRegistry all source EmbeddedHeroContent.pack(for: domain).{cat}
merged with a workspace disk layer, and extraction copies whatever hero's install
overlay emits per category. So category-level trims flow through faithfully for any
domain that IS extracted (engineering/pm/sales). BUT for chat specifically the trim
is a no-op on our side: chat isn't extracted, so there's nothing to flow. The
mechanism is safe; the caveat is the extraction-set gap, not the trim shape.

── Correction worth flagging: /ask-corpus is NOT consumed via the embedded pack ──
Your context assumes "/ask-corpus IS consumed (commands are staged)." Not through
the app's embedded content. /ask-corpus is a chat-pack command; it isn't in our
bundled engineering command set (verified — engineering ships blocked/capture/
deliver/design/… but no ask-corpus/corpus command), and chat isn't extracted. It
could only reach a chat session through the DISK layer — i.e. if `hero install`
wrote chat commands into the workspace harness dir (.claude/commands etc.) and the
registry merged them in. So on the embedded/bundled path, chat sessions see the
ENGINEERING command set, agents, skills, AND AGENTS.md — nothing from domains/chat/*.
If your evidence that /ask-corpus works comes from a Claude-Code/Codex harness
reading installed .claude files, that's a different consumer than the hero-code
desktop app and doesn't imply the desktop app serves chat-pack content.

── Bottom line / the real lever ──
The AGENTS.md-body-as-instructions channel is real and correct; keep authoring
ambient habits there. But for hero-code chat mode to pick them up, chat must become
an extractable, first-class pack: (1) go:embed the chat pack in hero so `hero domain
list` reports it [your action, the blocker], then (2) we stop mapping chat→engineering
in packDir(for:). Happy to take the hero-code half as a spec once the hero-side embed
lands. Until then, chat's AGENTS.md is decorative in this app and chat sessions run on
the engineering pack.
