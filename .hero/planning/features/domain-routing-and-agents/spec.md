## Goal

Move the natural-language routing table and the agent roster from
hardcoded repo-root files into the active domain pack. The agent loader
reads from `domains/<active>/agents/` and the routing table from
`domains/<active>/AGENTS.md`. A PM project routes to PM agents
(`product-strategist`, `story-writer`, `roadmap-curator`,
`intake-triager`) and presents the PM-shaped routing table; an
engineering project keeps today's behavior unchanged.

## Why now

Without this, the model routes to engineering agents inside a PM
project because the hardcoded routing table is engineering-shaped. The
parent initiative names this as a P0 platform primitive: the active
pack's routing table must be authoritative for natural-language intent
mapping, agent discovery, and the slash-command-to-agent dispatch.

The engineering routing table in `CLAUDE.md` today is the reference
shape — it moves into `domains/engineering/AGENTS.md` and becomes the
template for every other domain's table.

## Scope outline

The design pass should cover:

1. **AGENTS.md ownership.** Move `./AGENTS.md` into
   `domains/engineering/AGENTS.md`. Root-level `AGENTS.md` becomes
   either a symlink generated by `hero install` or absent (and the
   loader reads the active pack directly).
2. **Routing table relocation.** The natural-language intent table
   currently in `CLAUDE.md` (`User intent` → `Command`) is
   engineering-shaped. Move it into
   `domains/engineering/AGENTS.md`. Keep `CLAUDE.md` as a thin
   pointer to the active pack's table.
3. **Agent loader.** Whatever code discovers agents today (likely a
   filesystem walk under `./agents/`) reads from
   `domains/<active>/agents/` instead. Agents from inactive packs
   are not discoverable.
4. **`hero install` integration.** When `hero install` runs, it
   materializes the active pack's `AGENTS.md` and agent files into
   the project. `hero domain switch` re-installs from the new pack.
5. **Cross-domain workflows still work.** `/design`, `/deliver`,
   `/diagnose` remain accessible from any domain even if their
   "owning" agents are engineering-shaped — the routing table is
   per-domain, but the command surface can route into shared agents.
   This is the subtle bit; pin it down in design.
6. **Engineering reference shape.** `domains/engineering/AGENTS.md`
   carries the current 33 agents and the existing routing table,
   bit-identical to today's behavior.

## Unknowns for design pass

1. **Multi-active-domain loader behavior.** What happens when domains
   coexist (covered by primitive #6,
   `domain-scoped-knowledge-graph`)? The loader needs a stance:
   single-active-domain v1, multi-active deferred? Most likely yes —
   pin it down so this spec doesn't pretend to solve coexistence.
2. **`CLAUDE.md` vs `AGENTS.md` ownership.** Today `CLAUDE.md` holds
   the natural-language routing table; `AGENTS.md` holds the agent
   roster. After this work, do both live in the domain pack? Just
   `AGENTS.md`? `CLAUDE.md` becomes a pointer? Decide in design.
3. **Cross-domain agent reuse.** Some agents (e.g. `engineer`,
   `architect`) may be useful across domains. Is there a "shared"
   agent tier, or does each pack ship its own copy? Sharing is
   tempting but breaks the "pack is the unit of swap" model.
4. **Dashboard agent picker.** If the dashboard shows an agent picker
   anywhere, it should enumerate the active pack only. Confirm in
   design whether this surface exists today and needs updating.
5. **Symlink vs generated file.** `hero install` could symlink the
   pack's `AGENTS.md` to the project root or copy it. Symlinks break
   on Windows; copies drift. Pick during design.

## Boundaries

- **Not** designing PM agents — those land in `hero-pm`.
- **Not** supporting multiple active domains in one workspace v1.
- **Not** changing the agent contract (system prompt + tool surface)
  — only how they're discovered and routed.
- **Not** touching skills — skills are loaded independently and are
  already in `domains/<active>/skills/` per primitive #1.

## Risks

- **Routing-table tone matters.** The PM routing table will be the
  template the user sees in fresh PM projects; the table's voice
  shapes the product feel. Engineering's table is terse and
  declarative — match that.
- **Cross-domain command surface is the easiest place to break.**
  `/design` accepting a PM `story` and producing an engineering
  `feature` (per `hero-pm`'s killer demo) only works if the routing
  layer doesn't reject the cross-domain command. Pin this down.
- **Agent loader cache invalidation.** If `hero domain switch`
  doesn't fully re-load the agent registry, the model will hallucinate
  agents from the previous pack. Verify in design.
