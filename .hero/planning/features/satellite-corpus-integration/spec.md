# Satellite Corpus Integration — Scope as a First-Class Facet

## Problem

The previous spec ([monorepo-satellite-installs](../monorepo-satellite-installs/spec.md)) shipped the install/symlink/manifest layer plus first-pass scope stamping in `hero note`. Three loose ends remain before subproject scope actually compounds into corpus the way conventions or tags do:

1. **Skills don't inject scope.** When a user runs `/design` or `/diagnose` from inside a satellite folder, the slash command emits a prompt to the model. The CLI knows the active scope (we surfaced it in `hero status`), but the slash-command prompt itself doesn't tell the model. So the model writes a spec without `subproject:` frontmatter — the user has to remember to add it, or run `hero spec stamp-scope` after the fact. That's friction the install spec promised to remove.

2. **The graph and read surfaces don't index scope.** The `Spec` struct has the field, the parser reads it, the file stamps land on disk — but nothing flows downstream. `hero list`, `hero search`, `hero recap`, `hero feed` all ignore `subproject`. So even with stamps, you can't ask "show me everything in scope `engines/mlx`" without grepping. The corpus that's supposed to compound by scope doesn't.

3. **Migration execution is plan-only.** `hero install satellites --migrate-nested` prints what would happen but doesn't move anything. example codebase still has its three nested `.hero/` directories. The final step — actually moving spec/knowledge/event files into the root corpus with scope-stamped frontmatter, then materializing the satellite — is missing.

## Goal

Close the three loops so subproject scope is a first-class corpus facet:

- Slash commands that create artifacts inject the active scope into the prompt, so the model stamps `subproject:` automatically and the user never has to think about it.
- The index and the existing read surfaces (`list`, `search`, `recap`, `feed`) accept a `--subproject` filter and surface scope where it's useful.
- `hero install satellites --migrate-nested --apply` actually executes the migration plan, with `--dry-run` preserved as the safe default.

**Mission-fit.** The previous spec made satellites *possible*; this spec makes them *useful*. Without scope flowing through to read surfaces, a teammate running `hero recap` in a satellite still sees the whole repo's noise. Without skill injection, the user shoulders the stamping. Without migration execution, example codebase stays fragmented.

The non-goal is per-scope graph traversal weighting (e.g. boosting in-scope specs in `hero why`). That's a follow-on once we see how scope-filtered queries actually get used.

## Design

Three components, one per loose end. Each is independently testable and independently shippable, but they form a coherent slice — together they make scope work end-to-end.

### 1. Slash-command scope injection

The slash commands that create or modify hero artifacts are: `design`, `diagnose`, `deliver`, `note`, `capture`, `convention`, `decide`. (`deliver` itself doesn't create new specs but operates on one — out of scope here.)

Each emits a prompt template that goes to the model. The change is mechanical: prepend a small "active scope" preamble when the slash command runs from a scoped cwd.

The preamble is generated by a new `hero context scope` command (cheap, machine-readable) that returns:

```
WORKSPACE: /abs/path/to/root
SCOPE:     engines/mlx
SATELLITE: yes (engines/mlx)

Any spec, knowledge, or note you create in this session must include
`subproject: engines/mlx` in its YAML frontmatter, and must be written
under `<WORKSPACE>/.hero/...` regardless of the cwd this session is
running in.
```

The slash-command markdown templates are generated content (shipped in the install). The simplest wiring is to update each template to call `hero context scope` and prepend the result, the same way `/design` already calls `hero_anchor` for mission alignment. The skill files in `skills/` stay unchanged; only the slash-command files in `commands/` need a one-line addition near the top.

When `hero context scope` is run at root with no scope, it prints nothing and exits 0 — so the preamble is empty and the prompt is unchanged. No new conditional logic in templates.

**Why a CLI command instead of inlining the scope into each template?** Templates are static markdown, but scope is dynamic per-cwd. Calling out to a Hero command is the same pattern `hero_anchor` uses. It also means one place to evolve the preamble (e.g. add subproject description, related specs in scope) without re-editing every template.

**Why generate the preamble even for commands that don't create files (e.g. `/blocked`, `/check`)?** They don't get the preamble — only the artifact-creating commands listed above. The preamble is about telling the model "stamp this," which is meaningless for read-only commands.

### 2. Index + filter surfaces

Add `subproject` to the index schema and populate it on every spec ingest. Surface it as a filter on the read paths.

**Schema evolution.** Existing index migrations use `ALTER TABLE … ADD COLUMN` ignoring "duplicate column" errors — that's how `tracker_id` was added. Same pattern:

```sql
ALTER TABLE specs ADD COLUMN subproject TEXT NOT NULL DEFAULT ''
CREATE INDEX idx_specs_subproject ON specs(subproject) WHERE subproject != ''
```

**Ingest.** The existing `IndexSpec` upsert gains a `subproject` column. `Spec.Subproject` is read at parse time (already wired), so this is purely a SQL change.

**Read surfaces.** Add `--subproject <name>` to:

- `hero list` — filters specs to those carrying the scope
- `hero search` — restricts FTS query results to scope
- `hero queue` — orders/filters the scope's open specs
- `hero recap` — limits the recap to events tagged with this scope
- `hero feed` — limits the activity feed to this scope

When invoked from a satellite or scoped cwd *without* `--subproject`, the commands default to the active scope (with a one-line "showing scope: X — pass `--subproject all` for the full workspace" hint). Explicit `--subproject all` shows the unfiltered set. This is the right default: most of the time, when you're in `engines/mlx`, you mean "show me mlx stuff."

**Recap and feed event tagging.** Feed events written from a scoped session include the `subproject` field. The existing `FeedEvent` struct gains the field — backward-compatible because old events parse with empty subproject. Recap respects the filter the same way.

**Status nudge.** When the user is in a scoped cwd and runs a non-prefixed command, surface a one-time hint: "you're in scope `engines/mlx` — `hero list` will show only this scope's specs by default. Pass `--subproject all` for the full workspace." The hint stores a per-scope acknowledgment in `.hero/satellites.local.json` so it doesn't repeat.

### 3. Migration execution

Promote the existing `PlanMigration` into a two-mode command:

- `hero install satellites --migrate-nested` (default, dry-run) — current behavior, prints the plan, writes nothing.
- `hero install satellites --migrate-nested --apply` — executes the plan with explicit confirmation.

**Execution steps for one nested workspace at `<root>/<sub>/.hero/`:**

1. **Ack with the user.** Print the plan, then ask `Apply this migration? [y/N]`. Non-tty refuses without `--yes` (which is also accepted).
2. **Check for uncommitted changes** in the nested `.hero/` and the destination paths under root. Refuse if either is dirty without `--force`. Migration is destructive; an uncommitted spec edit would be lost.
3. **Move specs.** Each `<sub>/.hero/planning/<bucket>/<slug>/spec.md` moves to `<root>/.hero/planning/<bucket>/<slug>/spec.md`, with the spec's frontmatter rewritten to include `subproject: <sub>`. Slug collisions get a `-from-<sub>` suffix on the path (not the slug — the slug stays canonical for graph identity).
4. **Move knowledge.** Same pattern: `<sub>/.hero/knowledge/<type>/<name>` → `<root>/.hero/knowledge/<type>/<name>`, with subproject stamped if the file has frontmatter. Files without frontmatter get a sibling `_meta.yaml` recording the subproject.
5. **Append events.** `<sub>/.hero/events.log` is appended to `<root>/.hero/events.log` line-by-line, each line decorated with a `migrated_from: <sub>` field if the line is JSON; non-JSON lines get a comment prefix.
6. **Remove the nested workspace.** `<sub>/.hero/` is deleted. The user is told to commit the migration as a single commit.
7. **Materialize the satellite.** Reuse the existing `Materialize` path, register in `satellites.local.json`, add to `subprojects.json` if not already there.
8. **Re-index.** Call `hero index` to rebuild from the consolidated tree. Graph state is regenerated; merging two graph DBs is the wrong model when index is cheap.

**Idempotency.** Re-running `--apply` after a successful migration finds no nested `.hero/` and is a no-op. Re-running after a partial failure (e.g. moved 3 specs of 5, then crashed) detects the half-state and refuses without `--force-resume`, which finishes the unmoved files. This matters more than it sounds: a crash in step 3 with `git mv` half-applied is the kind of state someone's going to hit.

**Atomicity.** Every move uses `git mv` if the file is git-tracked, else `os.Rename`. On failure mid-stream, the migration logs what got moved and exits non-zero. The user sees exactly which files are in the new tree vs the old, can `git stash` and try again, or revert. We don't try to roll back partially completed moves — that adds complexity for a worse experience than letting the user resolve with normal git tools.

**Multi-nested.** When multiple subprojects have nested `.hero/` (example codebase's case: mlx + cuda), the command processes them sequentially. Failure on one stops the run with the consolidated tree partially populated; the user can re-run `--apply --force-resume` to finish.

### Design decisions

**Why a `hero context scope` command instead of inlining scope into each slash-command template at install time?** Templates are written to disk once; scope changes per-cwd. We could regenerate templates on every cwd change, but that's a sync invariant we don't need. Calling out to `hero context scope` makes scope a runtime fact, not a build-time one — same model as `hero_anchor`.

**Why default `--subproject` to the active scope when running from a satellite?** The whole point of being in `engines/mlx` is that you care about mlx. Showing the full corpus by default makes the satellite the worse experience than the root. The "showing scope: X" hint plus `--subproject all` covers the case where someone wanted the wider view; the friction is one flag, paid once when needed.

**Why store the "you're in a scope" hint acknowledgment in `satellites.local.json` rather than not storing it?** Repeating the hint every command is annoying. Per-machine ack means the developer sees it once per scope, then it stays out of the way. Per-machine matters because a teammate cloning the repo will see it the first time *they* run a scoped command — appropriate.

**Why use `git mv` when the file is tracked, plain `os.Rename` otherwise?** Git-tracking the move preserves history. Plain rename is fine for files outside git (e.g. the local sqlite indexes that get gitignored). Detecting tracked vs not is a single `git ls-files` call up front.

**Why refuse on dirty git state instead of stashing?** Stashing is a side effect we shouldn't impose. The user might be in the middle of unrelated work. A clear error pointing to `git stash` is the right default.

**Why re-index from scratch instead of merging graph DBs?** Index is fast (under a second on example codebase-sized repos), and a merge invariant across two DBs is its own bug surface. The simpler model is: graph DB is a cache, source of truth is the file tree, so rebuild after any structural change.

**Why does migration step 3 use a path suffix (`<bucket>/<slug>-from-<sub>`) on collisions instead of renaming the slug?** The slug is the spec's identity in the graph. If you rename it, every existing reference (in feed events, in other specs' relations, in tracker metadata) breaks. Path-only disambiguation keeps the slug stable.

**Why does `hero recap --subproject` filter events by subproject when events are project-wide?** Events written from a scoped session carry the subproject field (small backward-compat addition to `FeedEvent`). The filter applies post-hoc to events that had scope; events without scope (older events, or root-scope events) are excluded by the filter. This is the same shape as filtering by `--type` or `--since`.

**Why ship the slash-command preamble injection and the index filters in the same spec?** Because they're symmetrical: stamping is the write side, filtering is the read side. Shipping one without the other leaves the corpus half-integrated — either you stamp but can't query, or you query but the stamps aren't there. Together they close the loop.

## Acceptance Criteria

- THE SYSTEM SHALL provide a `hero context scope` command that prints a multi-line preamble (workspace path, scope id, satellite flag, stamping instruction) when invoked from a satellite or scoped cwd, and prints nothing (exit 0) when invoked at root with no scope.
- WHEN the `/design`, `/diagnose`, `/note`, `/capture`, `/convention`, `/decide` slash commands run from a scoped cwd THE SYSTEM SHALL include the `hero context scope` preamble in the prompt sent to the model.
- THE SYSTEM SHALL add a `subproject TEXT NOT NULL DEFAULT ''` column to the index `specs` table via the existing schema-evolution mechanism, idempotent across re-opens.
- WHEN a spec is indexed THE SYSTEM SHALL persist its `Subproject` field into the `subproject` column of the `specs` row.
- THE SYSTEM SHALL accept a `--subproject <name|"all">` flag on `hero list`, `hero search`, `hero queue`, `hero recap`, `hero feed`. Passing `all` disables filtering. Omitting the flag from a satellite or scoped cwd defaults to the active scope.
- WHEN a satellite-scoped command applies a default-scope filter THE SYSTEM SHALL print a one-line hint identifying the active scope and the `--subproject all` escape hatch, and SHALL suppress the hint on re-invocation within the same scope per-machine (acknowledgment stored in `.hero/satellites.local.json`).
- THE SYSTEM SHALL extend `FeedEvent` with a `subproject string` field and SHALL populate it when the event is emitted from a scoped session. Old events parse with empty `subproject` for backward compatibility.
- WHEN `hero recap` or `hero feed` is invoked with `--subproject <name>` THE SYSTEM SHALL filter events to those whose `subproject` field matches the name.
- THE SYSTEM SHALL provide `hero install satellites --migrate-nested --apply` to execute a migration plan against one or more nested `.hero/` workspaces under root, with `--dry-run` (no `--apply`) preserved as the default behavior.
- WHEN `--migrate-nested --apply` is invoked AND the user has not passed `--yes` AND stdin is a terminal THE SYSTEM SHALL display the plan and prompt for explicit y/N confirmation before any move.
- IF the workspace has uncommitted changes in the affected paths THEN THE SYSTEM SHALL refuse the migration and direct the user to commit or stash, unless `--force` is passed.
- WHEN migrating a spec THE SYSTEM SHALL move the spec.md file to the equivalent path under root, rewrite its frontmatter to include `subproject: <sub>`, preserve git history via `git mv` when the file is tracked, and disambiguate path collisions by suffixing the destination path with `-from-<sub>` while keeping the slug unchanged.
- WHEN migrating knowledge files THE SYSTEM SHALL move them to the equivalent path under root, stamping `subproject: <sub>` into frontmatter when present and writing a sibling `_meta.yaml` when not.
- WHEN migrating an `events.log` file THE SYSTEM SHALL append each line to the root events.log, decorating JSON lines with a `migrated_from: <sub>` field and prefixing non-JSON lines with a comment marker.
- WHEN migration of a nested workspace completes successfully THE SYSTEM SHALL delete the nested `.hero/` directory, materialize the satellite via the existing `Materialize` path, register it in `satellites.local.json`, ensure `subprojects.json` declares the subproject, and trigger a `hero index` rebuild.
- WHEN multiple nested workspaces are present THE SYSTEM SHALL process them sequentially and SHALL halt on the first failure with a clear log of what moved and what did not.
- WHEN `--migrate-nested --apply` is re-run after a partial failure THE SYSTEM SHALL detect the half-state and refuse without `--force-resume`; with `--force-resume` THE SYSTEM SHALL complete the unmoved files only.
- WHEN `--migrate-nested --apply` is re-run after a fully successful migration THE SYSTEM SHALL exit cleanly with no nested workspaces to migrate.
- THE SYSTEM SHALL NOT roll back partially completed file moves on failure — the migration log identifies what landed where and the user resolves with normal git tools.

## Phasing

### Phase 1 — Skill prompt scope injection
The smallest, highest-leverage change. Adds the `hero context scope` command and updates the six artifact-creating slash-command templates to call it. Acceptance: a fresh chat opened in `engines/mlx` and triggered with `/note "test"` produces a note frontmatter that includes `subproject: engines/mlx` without any further user action.

### Phase 2 — Index column + filter surfaces
Adds the `subproject` column to the index, populates on ingest, threads `--subproject` through `list / search / queue / recap / feed`. Adds the satellite-scoped default behavior with the one-time hint. `FeedEvent.Subproject` field plus emission from scoped sessions. Acceptance: `cd engines/mlx && hero list` shows only mlx-scoped specs; `hero list --subproject all` shows everything; new feed events from scoped sessions carry the field.

### Phase 3 — Migration execution
Promotes `PlanMigration` from plan-only to plan+apply. Adds confirmation prompt, dirty-git refusal, the per-step move logic with `git mv` preference, the post-migration satellite materialization and index rebuild, and the partial-failure / `--force-resume` handling. Acceptance: example codebase's three nested `.hero/` directories migrate to satellites with one command, history-preserving on tracked files, and a re-run is a no-op.
