# Cross-Repo Peering Protocol

## The rule

> When work in one Hero workspace touches a sibling workspace's
> surface, pick one of three interaction modes — **sync peer call**,
> **async handoff**, or **convention import** — and let the protocol
> carry the provenance. Never ferry context by hand between two
> sessions in two repos.

The protocol is local-first: three sibling checkouts on a laptop
with no cloud is the canonical case. Cloud federation (v2+) layers
the same shapes over a different transport.

## The three-tier ladder

Pick a mode by what the work needs, not what feels easy:

| Mode | Writes? | Returns | Pick when |
|---|---|---|---|
| **Sync peer call: advisory** | Nothing | Findings text | You need a *fact* from peer B — "does this break you?", "what's your convention for X?", "is there already an endpoint for this?" |
| **Sync peer call: spec-out** | Spec on B | Peer spec slug + handoff state | You realized this is *really* B's work and you want B's Hero to design it natively — its conventions kick in for free, the spec persists. |
| **Async handoff** | Spec on B (scaffolded) | Peer spec slug | You already did the investigation; you want to drop it on B's queue and walk away. |
| **Convention import (fallback)** | Nothing | Conventions in A's context | Work *legitimately* stays in A but must respect B's surface — e.g. a serializer in A producing a payload B parses. |

Sync peer call full-delivery (mode=full) is v2+ — gated by approval
and budget. Not in v1.

## Identity: peer_id is the join key

Every workspace mints a stable UUID at `hero init` and writes it to
`hero.json` as `peer_id`. Manifests, handoff records, trail entries,
and peer-call envelopes reference peers by `peer_id`. Local aliases
(`hero repos add app ../app`) are the human-readable display form
and can disagree across machines without breaking peering.

If you see `peer_id` mismatches between sides of a handoff, that's
the bug — alias mismatches are not.

## Manifest publishing — opt-in only

A workspace's `peer-manifest.yaml` (under `.hero/`, generated by
`hero index`) publishes:

- The workspace's `peer_id` + display name.
- Every convention explicitly marked **peer-surface** — via
  `peer: true` in convention frontmatter, or by slug/glob match
  in `hero.json: peering.publish_conventions`. Default is empty.
- A `contracts:` section listing Go symbols this workspace owns,
  each with a governing convention slug.

Default publish set is empty. Principle of least authority. A
peer's session sees only what you've explicitly chosen to expose —
your internal style guide stays internal.

## Handoff lifecycle and statuses

A spec moves through these states as it crosses the boundary:

```
delivering    →  handed_off     ← `hero handoff` runs; receiver
                                  scaffold lands; trail entry written.

handed_off    →  awaiting_peer  ← peer-side spec hits `delivering`.
                                  Reconciled at `hero status` render.

awaiting_peer →  handed_back    ← peer-side spec hits `completed`.
                                  Reconciled at `hero status` render.
                                  Trail entry carries `result_ref`
                                  (commit / PR / completion event).

handed_back   →  delivering     ← `hero handoff accept <slug>` —
                  or  completed   user picks next phase.
```

Specs in `handed_off` and `awaiting_peer` are excluded from the
active-delivering invariant in `spec-status-integrity`. They are
*in flight at the peer*, not at you.

## The Handoff Trail

Every cross-workspace event lands as a `## Handoff Trail` entry on
both the originator's and receiver's specs. The trail is the audit
log — never rely on `events.log` alone to reconstruct what
happened. A trail entry carries:

- `at` — UTC timestamp.
- `direction` — `out` (you sent) or `in` (you received).
- `peer_alias_display` — the peer's local alias on your side.
- `peer_id` — the peer's canonical UUID.
- `mode` — `async-drop`, `advisory`, `spec-out`, `handed-back`, etc.
- `originating_spec` / `peer_spec` — the `<alias>/<slug>` cross-refs.
- `peer_status` — the peer's status at the moment of the entry.
- `result_ref` — for handed-back: commit SHA, PR URL, or completion
  artifact path.
- `reason` — free-form rationale.

`CrossRepoResolver` walks the trail in either direction, so given
either side of a handoff you can reach the other.

## Contract imports as the boundary detector

When a session in repo A edits a file that imports a Go symbol
listed in any configured peer's manifest `contracts:` section,
`/resume` and `hero context imports` add a one-line passive signal:

```
- `contracts/events.Envelope` in `src/api/orders.go` — owned by
  peer `app` (peer_id: 9c1c2f3e…). Convention: error-envelope.
  Last changed: commit 4427cec.
```

No blocking, no prompts, no auto-call. Just signal. "This file
imports a peer-owned contract symbol" is the cleanest signal that
a change crosses a repo boundary — cleaner than path heuristics or
commit-message scanning.

Non-matches: test files (`*_test.go`), generated code (canonical
`// Code generated ... DO NOT EDIT.` header), and files under
`vendor/`. The signal is for real consumers, not fixtures.

## Local-first transport, cloud augments

**v1 (now):** all cross-repo reads and writes go through `hero
repos`-resolved sibling paths on local disk. No daemon, no network,
no login required.

**v2+ (deferred):** when `cloud.org_id` is set, the same shapes
flow over a server-mediated transport — peer manifests published to
the cloud graph, handoffs routed by `peer_id`. Same data, different
transport.

If a peer isn't reachable on local disk and cloud isn't configured,
the protocol fails fast with "peer not reachable; mirror via cloud
or wait." No SSH-into-peer, no fancy daemon.

## Where the shapes live

All wire shapes live in `contracts/peering/`:

- `manifest.go` — `PeerManifest`, `ConventionEntry`,
  `ContractEntry`, `ContractsSection`, `RepoIdentity`.
- `handoff.go` — `HandoffRecord`, `ReceivedFrom`,
  `HandoffStatus`, `TrailEntry`, `TrailDirection`, `TrailMode`.
- `peercall.go` — `PeerCallRequest`, `PeerCallResult`,
  `PeerCallMode`, `BudgetSpec`, `BudgetConsumed`.
- `events.go` — `peer.handoff.*` and `peer.call.*` event envelopes.
- `version.go` — `PeeringContractsVersion`, evolved **independently**
  of the main `ContractsVersion` so peering shape bumps don't drag
  the cloud-split contract version with them.

Producers live in `internal/peering/`; the CLI surface in
`internal/cli/handoff.go` and `internal/cli/peer.go`.

## Dogfood checklist (Phase 3 exit gate)

Before opening Phase 4 (cloud transport + boundary nudge), run this
ladder against three real sibling repos and ask "did this feel like
a tag team, or like ceremony?" If ceremony, fix before adding more
modes.

Set up:

- [ ] All three repos have `peer_id` minted in `hero.json` (run
  `hero` once in each; check the events log for
  `workspace.peer_id_minted`).
- [ ] Each repo's `hero.json: repos` lists the other two by alias
  pointing at sibling paths.
- [ ] `hero index` has run in each — each `.hero/peer-manifest.yaml`
  exists.
- [ ] At least one peer-surface convention is published in each
  manifest (frontmatter `peer: true` on the convention, or
  slug/glob in `peering.publish_conventions`).
- [ ] `app` (or your backend) publishes at least one contract
  shape under `contracts:` in its peer manifest.

Ladder — from a `client` session, against `app`:

- [ ] **Advisory call.** `hero peer call app --mode=advisory
  "What's your error envelope shape today?"` returns findings
  without writing anything on `app`'s side. Trail entry appears
  on the related spec.
- [ ] **Spec-out call.** `hero peer call app --mode=spec-out
  --related-spec <slug> "Design the backend fix for X"` produces
  a `planning`-status spec under `<app>/.hero/planning/...` with
  `received_from` pointing at your client spec; your spec's
  status moves to `awaiting_peer`; trail entries land on both
  sides.
- [ ] **Async handoff.** `hero handoff <slug> app --reason "..."`
  scaffolds a peer spec on `app`; your spec moves to `handed_off`;
  both sides carry trail entries.
- [ ] **Receiver-side queue.** Switch to `app`. `hero queue` shows
  the incoming handoff distinct from local-origin work.
- [ ] **Peer-side completion auto-fires the return signal.** On
  `app`'s side, drive the handed-off spec to `delivering` →
  `completed` (real work or stub). Switch back to `client`. `hero
  status` shows the spec as `handed_back` with a trail entry
  pointing at the completion artifact.
- [ ] **Contract-import passive surfacing.** In `client`, edit a
  Go file that imports an `app`-owned contract symbol. Run
  `/resume` or `hero context imports`. The one-line signal
  appears naming the symbol, peer alias, convention slug, and
  last-changed commit. Repeat with the import in a `*_test.go`
  file — the signal must NOT appear.
- [ ] **Convention import fallback.** `hero relevant src/foo.ts
  --peer app` pulls `app`'s peer-surface conventions into your
  context.

Ergonomic gut-check after the ladder:

- [ ] Did context-switching between `client` and `app` feel like
  *the same tool* coordinating two repos, or like running two
  separate tools that happen to talk?
- [ ] Did `hero queue` + `/resume` at session-switch time give
  you enough situational awareness, or did you keep grepping the
  other repo?
- [ ] Did the spec-out spec produced on `app`'s side feel like
  something `app`'s Hero designed, or like a paste-job from
  `client`?
- [ ] Is the boundary signal informative or noisy? Too many hits
  means the contract surface is over-published; zero hits when
  you'd expect some means it's under-published.

If any answer skews toward "ceremony" — file a bug or scope a
Phase 3.5 ergonomics pass before unlocking Phase 4.

## Why it exists

The compounding promise of Hero — *the next session starts smarter
than the last one ended* — used to stop at the repo boundary. Cross
a boundary and conventions disappeared, handoffs were paste-jobs,
and the peer's Hero never saw the spec it inherited. The peering
protocol carries provenance across that boundary so the same
compounding works when work is *split across repos*, not just
across sessions in one repo.

The local-first stance is non-negotiable in v1 — peering must work
on a laptop with three sibling checkouts and no login. Cloud
federation reuses the same wire shapes when it lands.
