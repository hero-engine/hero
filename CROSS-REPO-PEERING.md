# Cross-Repo Peering

Make sibling Hero workspaces — a Go backend, a web client, a desktop
client — work as a tag team. When a session in repo A touches repo B's
surface, you can:

- **Ask B's Hero a question** (sync peer call, advisory).
- **Have B's Hero design a spec** with its own conventions baked in
  (sync peer call, spec-out).
- **Drop a spec on B's queue** and walk away (async handoff).
- **Pull B's peer-surface conventions** into A's context as a fallback.

Provenance travels with every operation. No more paste-jobs across
sessions.

This guide covers v1, which runs **on a developer laptop with three
sibling checkouts and no cloud**.

---

## What this solves

Today, when a session in the client touches the backend's API surface,
the backend's conventions (error shapes, auth flow, naming) aren't
loaded. The client's Hero writes a change that runs face-first into the
backend's expectations.

The same gap shows up the other way: when the user concludes "this is
really a backend job," the path used to be — write a spec on the
backend by hand, paste in context from the client's session, hope the
backend's Hero notices. No first-class handoff, no provenance, no
return signal.

Cross-repo peering carries the protocol — three interaction modes plus
a passive boundary detector — so the compounding promise of Hero (the
next session starts smarter than the last one ended) keeps working
when the work is split across repos.

---

## The three-tier ladder

Pick a mode by what the work needs:

| Mode | Writes? | Returns | Pick when |
|---|---|---|---|
| **Sync peer call — advisory** | Nothing | Findings text | You need a fact from peer B: "does this break you?", "what's your error envelope?", "is there already an endpoint for this?" |
| **Sync peer call — spec-out** | Spec on B (`status: planning`) | Peer spec slug + handoff state | You realized the work is really B's. B's Hero designs the spec natively; B's conventions kick in for free. |
| **Async handoff** | Spec on B (scaffolded) | Peer spec slug | You already did the investigation; drop it on B's queue. |
| **Convention import (fallback)** | Nothing | Conventions in A's context | Work stays in A but must respect B's surface — e.g. a serializer in A producing a payload B parses. |

Full-delivery sync peer call (B designs *and* delivers, returns a
commit/PR) is v2 — out of scope for v1.

## Setup

### 1. Confirm each repo has a `peer_id`

Every Hero workspace needs a stable UUID in `hero.json` under `peer_id`.
`hero init` mints one on new workspaces. Existing workspaces get one
**automatically** the first time any `hero` command runs after upgrade,
with a `workspace.peer_id_minted` entry in `.hero/events.log`.

```bash
cd /path/to/each/repo
hero status                       # any command triggers the migration
grep peer_id .hero/hero.json
```

`peer_id` is the canonical join key for handoff records, trail entries,
and peer-call envelopes. Local aliases (next step) are the
human-readable display form only — two machines can disagree on
aliases without breaking peering.

### 2. Register each sibling as a peer

Run `hero admin repos add` in each workspace, once per sibling:

```bash
# In the client workspace:
hero admin repos add app ../app
hero admin repos add desktop ../desktop

# In the app workspace:
hero admin repos add client ../client
hero admin repos add desktop ../desktop

# And so on.
```

`hero admin repos scan` will auto-discover Hero workspaces in the parent
directory if your sibling layout is conventional:

```bash
hero admin repos scan --auto
```

Both `add` and `scan` read the sibling's `hero.json:peer_id` and record
it in the local registry alongside the alias.

### 3. Generate each peer manifest

The peer manifest is what siblings *read* to learn what you're
publishing. It's generated by `hero index`:

```bash
cd /path/to/each/repo
hero index
ls .hero/peer-manifest.yaml
```

You can regenerate the manifest standalone without a full reindex:

```bash
hero peer manifest
```

### 4. Mark conventions as peer-surface

Default publish set is **empty**. Principle of least authority — your
internal style guide stays internal until you opt in. Two ways to
publish a convention:

**Per-convention frontmatter flag:**

```yaml
---
title: "Standard error envelope shape"
type: convention
status: active
peer: true
peer_surface: [http-response, sse-event]
---
```

The `peer_surface` list controls which surface tags the convention
matches when consumers filter with `hero relevant --surface <tag>`.

**Glob list in `hero.json`:**

```json
{
  "peering": {
    "publish_conventions": ["error-envelope", "auth-*"]
  }
}
```

Each entry is a slug or glob. After editing either, rerun `hero peer
manifest` (or `hero index`) to refresh.

### 5. Declare contract shapes (Go consumers only in v1)

If consumers in other repos import Go symbols you own, list them in the
`contracts:` section of the manifest. Today the manifest contracts
section is populated by the manifest generator from the workspace's
`contracts/` package; for hand-authored entries, edit the file under
the `contracts:` block:

```yaml
contracts:
  package: github.com/hero-engine/hero/contracts
  version: 3
  shapes:
    - kind: event-envelope
      go_symbol: contracts/events.Envelope
      convention: error-envelope
    - kind: spec-frontmatter
      go_symbol: contracts/spec.Frontmatter
      convention: spec-format
```

Consuming sessions get a passive one-liner when they edit a Go file
that imports one of these symbols. See **Contract import surfacing**
below. Only Go imports are scanned in v1; TypeScript / Python / other
languages are deferred.

### 6. Configure the subagent (optional)

`hero peer call` shells out to a local LLM CLI in the peer's
workspace. Default: `claude` on PATH, invoked with `-p` for
non-interactive mode. To override:

```json
{
  "peering": {
    "subagent": {
      "command": "claude",
      "args": ["-p"],
      "env_passthrough": ["ANTHROPIC_API_KEY", "PATH", "HOME"]
    }
  }
}
```

Hero never holds an API key — the subagent inherits it via
`env_passthrough`. Budgets pass through as `HERO_PEER_CALL_BUDGET_TURNS`
and `HERO_PEER_CALL_BUDGET_TOKENS` env vars; the subagent honors them
at harness level.

## Common workflows

### A. Ask the backend a question (advisory call)

From the client repo, mid-session, you want a fact from the backend.

```bash
hero peer call app --mode=advisory \
  "What's your error envelope shape today? Any deprecations in flight?"
```

What happens:

- A subagent spawns in `../app` with the app's full Hero context loaded.
- It investigates, prints a structured `<peer-call-result>` block.
- Hero parses the result and prints findings.
- **Nothing is written on the app side** beyond an event-log entry.

Tie the call to a local spec so the trail records it:

```bash
hero peer call app --mode=advisory \
  --related-spec order-failure-error-display \
  --reason "Need shape before I change the client renderer" \
  "What's your error envelope?"
```

Default budget: 20 turns / 50,000 tokens. Override with
`--budget-turns` and `--budget-tokens`.

Use `--dry-run` to print the envelope without dispatching the subagent
— useful for debugging.

### B. Ask the backend to design the fix (spec-out)

You realized the symptom is in the client but the real fix is on the
backend. You want the backend's Hero to design it natively, so its
conventions kick in.

```bash
hero peer call app --mode=spec-out \
  --related-spec order-failure-error-display \
  --reason "Symptom is in the client, root cause is the API response shape" \
  "Design the fix for the error envelope mismatch we saw in the client."
```

What happens:

- A subagent in `../app` runs the app's `/design` flow with your prompt.
- A spec lands at `../app/.hero/planning/<type>/<slug>/spec.md` with
  `status: planning` and a `received_from:` block referencing your spec.
- Your local spec moves to `status: awaiting_peer` with a trail entry.
- The backend's `hero queue` now shows the spec in **Incoming Handoffs**.

Default budget: 50 turns / 150,000 tokens.

### C. Drop an investigation on the backend (async handoff)

You already drafted the diagnosis in the client repo. The fix clearly
belongs on the backend. Hand it off:

```bash
hero handoff order-failure-error-display app \
  --reason "Symptom in client, root cause in API response shape" \
  --type bug
```

What happens:

- Your local spec's status moves to `handed_off` with a trail entry
  (direction: `out`, mode: `async-drop`).
- A scaffolded spec lands at `../app/.hero/planning/bug/<slug>/spec.md`
  with `status: planning`, a `received_from:` block, and a reciprocal
  trail entry (direction: `in`).
- Both sides get a `peer.handoff.*` event in their events log.

Optional flags:

- `--title "New title"` — override the receiver-side spec title (and
  derive a hand-picked slug if the default would collide).
- `--type feature|bug|...` — override the receiver-side spec type.

If the peer-side slug collides, Hero appends `-2`, `-3`, ... and
reports the chosen slug.

## Spec status lifecycle

A handed-off spec moves through these states. Statuses live in the
spec's frontmatter; transitions are reconciled at `hero status` render
time (no daemon).

| Status | Side | Meaning |
|---|---|---|
| `handed_off` | Originator | Just handed off. Receiver scaffold landed, trail entry written. |
| `awaiting_peer` | Originator | Peer-side spec is `delivering`. Ball's in their court. |
| `handed_back` | Originator | Peer-side spec is `completed`. Verify on your side. |
| `planning` (+ `received_from`) | Receiver | Standard lifecycle. The `received_from` block carries provenance. |

Specs in `handed_off` and `awaiting_peer` are excluded from the
active-delivering invariant in `spec-status-integrity` — they're in
flight at the peer, not at you.

When the peer's spec reaches `completed`, the originator's status
**auto-flips** from `awaiting_peer` to `handed_back` next time `hero
status` runs. A trail entry is appended with `result_ref` pointing at
the peer's commit or completion event. The originator's spec does
*not* auto-complete — you verify the symptom resolved.

To pick up a `handed_back` spec:

```bash
hero handoff accept <slug>
# Pick the next status for this spec:
#   1) delivering (default)
#   2) in-review
```

### Handoff Trail example

Every spec involved in a handoff or peer call carries a `## Handoff
Trail` section. Entries look like:

```markdown
## Handoff Trail

- 2026-05-15T14:00:00Z — out → app (peer_id: 9c1c2f3e-...)
  mode: async-drop
  originating_spec: order-failure-error-display
  peer_spec: app/error-envelope-mismatch
  at_commit: 3176736
  reason: "Symptom is in the client, root cause is the API response shape."

- 2026-05-15T16:23:00Z — in ← app (peer_id: 9c1c2f3e-...)
  mode: handed-back
  peer_spec: app/error-envelope-mismatch (status: completed)
  result_ref: commit 4427cec
```

`CrossRepoResolver` walks the trail in either direction — given either
side of a handoff, you can reach the other.

## Inspecting state

```bash
hero peer list
# ALIAS    PEER_ID                                 REACHABLE  MANIFEST  CONV  IN-FLIGHT
# app      9c1c2f3e-4a8b-4f9d-9a0e-7e1f0d8c3a55    yes        yes       3     1
# desktop  7b2a...                                 yes        no        -     0

hero peer show app
# Detail view: manifest contents, peer_id, reciprocity check, last
# index time, count of in-flight handoffs targeting this peer.

hero queue
# Incoming Handoffs section lists specs with received_from set.

hero status
# Surfaces handed-off specs whose peer side reached completed.

hero handoff status
# All in-flight handoffs.

hero handoff status <slug>
# One spec, with full trail.
```

`hero peer list` reciprocity check (in `hero peer show`) tells you
whether the peer lists *you* in its `hero admin repos` registry. A peer that
hasn't registered you back can still receive handoffs, but its `/resume`
won't surface your incoming work.

## Convention import (fallback)

When work legitimately stays in repo A but must respect repo B's
surface — e.g. a serializer in A producing a payload B parses — pull
B's peer-surface conventions into A's context:

```bash
hero relevant src/api/orders.go --peer app
hero relevant --peer app --surface http-response
hero relevant src/api/orders.go --peer app --peer shared-libs
```

This reads `<peer-path>/.hero/peer-manifest.yaml` and includes the
listed conventions in the relevant-context output. If the manifest is
missing or unreadable, the command fails with a clear pointer to run
`hero index` in the peer repo.

`--peer` is an explicit ask: Hero honors it even when the
`team.nudge_level` setting is `off`.

## Contract import surfacing

When a session edits Go files that import a peer-owned contract symbol
(listed under `contracts:` in any configured peer's manifest), `/resume`
and `hero context imports` add a one-line passive signal:

```
- contracts/events.Envelope in src/api/orders.go — owned by peer app
  (peer_id: 9c1c2f3e-...). Convention: error-envelope. Last changed:
  commit 4427cec.
```

This is the boundary *detector* powering the seamlessness goal:
"this file imports a peer-owned contract symbol" is cleaner than path
heuristics or commit-message scanning.

What's filtered out (no signal):

- Test files (`*_test.go`).
- Generated code (canonical `// Code generated ... DO NOT EDIT.` header).
- Files under `vendor/`.
- Files that import the *package* without referencing the listed symbol.

No prompts, no blocking, no auto-call. Just signal. The user decides
what to do with it.

You can query the signal directly:

```bash
hero context imports
```

This subcommand mirrors `hero context scope` and is what slash-command
templates call to surface the same one-liner.

## Configuration reference

All peering settings live in `.hero/hero.json`:

```json
{
  "peer_id": "9c1c2f3e-4a8b-4f9d-9a0e-7e1f0d8c3a55",
  "repos": {
    "app": "../app",
    "desktop": "../desktop"
  },
  "peering": {
    "display": "Hero Web Client",
    "scope_hint": "web",
    "publish_conventions": ["error-envelope", "auth-*"],
    "subagent": {
      "command": "claude",
      "args": ["-p"],
      "env_passthrough": ["ANTHROPIC_API_KEY", "PATH", "HOME"]
    }
  }
}
```

| Field | Purpose | Default |
|---|---|---|
| `peer_id` | Canonical UUID for this workspace. Minted by `hero init` or auto-migration. Never edit by hand. | (minted) |
| `peering.display` | Optional human-readable name in the manifest. | (workspace name) |
| `peering.scope_hint` | Optional role tag ("backend", "web", ...) in the manifest. | (empty) |
| `peering.publish_conventions` | Slugs or globs of conventions to publish without per-convention `peer: true`. | `[]` |
| `peering.subagent.command` | LLM CLI for sync peer calls. | `claude` |
| `peering.subagent.args` | Args before Hero-added flags. | `["-p"]` |
| `peering.subagent.env_passthrough` | Env vars forwarded to the subagent. | `["ANTHROPIC_API_KEY", "PATH", "HOME"]` |

Per-convention `peer: true` frontmatter is the per-file alternative to
`publish_conventions`.

## Troubleshooting

**`peer X is not configured`**
The alias isn't in `hero admin repos`. Run `hero admin repos add <alias> <path>`
or `hero admin repos scan --auto`.

**`manifest missing — run hero index in <peer-path>`**
The peer's `.hero/peer-manifest.yaml` doesn't exist. Switch to the peer
repo and run `hero index` (or `hero peer manifest`).

**`subagent command "claude" not found on PATH`**
Install the configured CLI, or override `peering.subagent.command` in
`hero.json` to point at one you have.

**`subagent timed out after 10m`**
The peer-side subagent exceeded the call timeout. Tune
`--budget-turns` / `--budget-tokens` downward, or check that the
subagent honors `HERO_PEER_CALL_BUDGET_*` env vars at harness level.

**Slug collision on receive**
`hero handoff` appends `-2`, `-3`, ... and reports the chosen slug.
Use `--title "New title"` to derive a hand-picked slug instead.

**Two-write atomicity warning from `hero check`**
The handoff writes receiver-spec-first, then originator-status. If the
second write fails, the peer spec exists with `received_from` but the
originator still shows the pre-handoff status. `hero check` surfaces
this as a recoverable inconsistency — re-running `hero handoff` is
idempotent and clears the warning.

**Duplicate `peer_id` across two clones**
If you cloned the same workspace twice and edited both, both clones
have the same `peer_id`. `hero check` surfaces this as a
duplicate-identity warning. Pick one to keep; in the other, delete
`peer_id` from `hero.json` and run any `hero` command to mint a fresh
one.

**Peer path not writable**
`hero handoff` and spec-out calls write into the peer's `.hero/`. If
the peer path lacks write permission, the operation fails fast with a
clear error before any state changes.

## What's not in v1

Explicit about expectations:

- **Full-delivery sync peer call** (B designs and delivers, returns
  commit/PR). v2 — gated by approval + budget.
- **`hero nudge` boundary suggestion** on structural contract edits.
  v2.
- **Auto-trigger advisory call** when contract shapes change. v3.
- **Cloud transport.** v1 requires peers to be siblings on local disk.
  Cross-machine peering rides on the cloud federation work that's still
  in flight.
- **Non-Go contract scanners.** Only Go imports are scanned in v1.
  TypeScript / JavaScript / Python / others are deferred.

## Dogfood checklist

Walk this against three real sibling repos before relying on the flow
in real work. The exit gate question: **did it feel like a tag team,
or like ceremony?**

Setup:

- [ ] All three repos have `peer_id` in `hero.json` (run any `hero`
  command in each; check `.hero/events.log` for `workspace.peer_id_minted`).
- [ ] Each repo's `hero.json: repos` lists the other two by alias
  pointing at sibling paths.
- [ ] `hero index` has run in each — every `.hero/peer-manifest.yaml`
  exists.
- [ ] At least one peer-surface convention is published in each manifest
  (`peer: true` in the convention's frontmatter, or slug/glob in
  `peering.publish_conventions`).
- [ ] The backend repo lists at least one contract shape under
  `contracts:` in its peer manifest.

Ladder — from a `client` session, against `app`:

- [ ] **Advisory call.** `hero peer call app --mode=advisory "What's
  your error envelope shape today?"` returns findings without writing
  anything on `app`'s side. Trail entry appears on the related spec.
- [ ] **Spec-out call.** `hero peer call app --mode=spec-out
  --related-spec <slug> "Design the backend fix for X"` produces a
  `planning`-status spec under `<app>/.hero/planning/...` with
  `received_from` pointing at your client spec. Your spec's status
  moves to `awaiting_peer`. Trail entries land on both sides.
- [ ] **Async handoff.** `hero handoff <slug> app --reason "..."`
  scaffolds a peer spec on `app`. Your spec moves to `handed_off`.
  Both sides carry trail entries.
- [ ] **Receiver-side queue.** Switch to `app`. `hero queue` shows
  the incoming handoff distinct from local-origin work.
- [ ] **Peer-side completion auto-fires the return signal.** On
  `app`'s side, drive the handed-off spec to `delivering` →
  `completed` (real work or a stub). Switch back to `client`. `hero
  status` shows the spec as `handed_back` with a trail entry pointing
  at the completion artifact.
- [ ] **Contract-import passive surfacing.** In `client`, edit a Go
  file that imports an `app`-owned contract symbol. Run `/resume` or
  `hero context imports`. The one-line signal appears naming the
  symbol, peer alias, convention slug, and last-changed commit. Repeat
  with the import in a `*_test.go` file — the signal must NOT appear.
- [ ] **Convention import fallback.** `hero relevant src/foo.ts --peer
  app` pulls `app`'s peer-surface conventions into your context.

Ergonomic gut-check after the ladder:

- [ ] Did context-switching between `client` and `app` feel like *the
  same tool* coordinating two repos, or like running two separate
  tools that happen to talk?
- [ ] Did `hero queue` + `/resume` at session-switch time give you
  enough situational awareness, or did you keep grepping the other
  repo?
- [ ] Did the spec-out spec produced on `app`'s side feel like
  something `app`'s Hero designed, or like a paste-job from `client`?
- [ ] Is the boundary signal informative or noisy? Too many hits means
  the contract surface is over-published; zero hits when you'd expect
  some means it's under-published.

If any answer skews toward ceremony — file a bug or scope an
ergonomics pass before relying on it daily.
